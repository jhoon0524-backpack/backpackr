## 선물·옵션 모델 구조 (엔티티 관계)

- **선물(`Reward`, table `rewards`)** — 프로젝트에 속한 후원 보상 단위. 주요 속성: `money`(금액), `title`(제목), `limit`(선물 총 제한 수량, null=무제한), `userLimit`(1인당 제한 수량, null=무제한), `type`(선물 유형), `order`(정렬), `backerCountCache`(후원 수 캐시), `preBackerCountCache`(사전예약 수 캐시), `slotNotificationCount`/`slotNotifiedAt`(빈자리 알림 관련), `recommended`(추천 선물 플래그 — REGULAR 중 프로젝트당 1개)
  - **추천 선물(`recommended=true`)의 `expected_delivery_date`는 프로젝트 예상 발송 시작일로 자동 덮어써지며 개별 편집 불가**(프로젝트→선물 단방향 연동, 코드 확인 2026-07-15). 연동 정책 상세는 03-project.md 「예상 발송 시작일」 소관.
  - **"선물 없이 후원"**: `money=1,000원`, `title="선물 없이 후원"`, `reward_id=0`인 가상 선물. DB에 저장되지 않고 요청 시 즉석 생성된다. 실물 전달이 필요 없는 후원 경로.
  - **선물 재고 소진 판정**: 한정 수량이 설정된(`limit` not null) 선물에서 `limit ≤ backerCountCache`이면 소진(품절) 상태.
  - 관계: 선물 1 — N 선물 구성 아이템(`RewardItem`을 통해 `Item`과 N:M) / 선물 1 — N 추가 정보(`AddInfo`) / 선물 1 — N 후원(`ProjectWarranty`)
- **선물 구성 아이템(`Item`, table `items`)** — 선물을 구성하는 개별 아이템. 하나의 선물은 여러 아이템으로 구성될 수 있다.
  - `optionType`(옵션 유형): `0`=옵션없음, `1`=주관식, `2`=객관식
  - `optionDesc`(객관식 선택지 원문) — 줄바꿈(`\n`) 문자로 구분된 문자열로 저장되며, 조회 시 이 구분자로 분리해 선택지 목록을 만든다.
  - `title`(아이템명), `order`(정렬)
- **선물↔아이템 연결(`RewardItem`, table `reward_items`)** — 선물과 아이템의 연결 관계 + `quantity`(해당 아이템에서 후원자가 선택해야 하는 옵션 개수).
- **추가 정보/설문 옵션(`AddInfo`, table `addinfos`)** — 선물에 붙는 추가 입력 항목(배송지·연락처 외 커스텀 질문 등). `title`, `description`, `answerType`(기본값 TEXT)을 가진다.
- **후원 시 추가정보 답변(`PurchaseAddInfo`, table `purchase_addinfos`)** — 후원 시점에 후원자가 입력한 추가정보 답변. `answer`(자유 텍스트), 우편번호·주소·전화번호 필드를 포함하며, 후원 1건당 추가정보 1개는 유일(unique 제약).
- **후원 시점 옵션 답변 스냅샷(`ProjectWarrantyRewardItem`, table `project_warranty_reward_items`)** — 후원자가 실제로 선택·입력한 옵션 값을 담는 스냅샷 레코드. `option` 값은 최대 1,500자까지 저장 가능(DB 컬럼 한도). `state`(0=삭제 안 됨, 1=삭제 — 중복후원 기능 배포 이후로는 사용되지 않음).
- **한정 선물 잔량 캐시(`ProjectLimitReward`, table `project_limit_rewards`)** — 한정 수량이 설정된 선물의 표시용 잔량(`remainQuantity`) 캐시. 최초 생성 시 `remainQuantity`는 선물의 `limit` 값으로 초기화된다.

## 주관식 옵션 허용 문자 (노션 정책)

주관식 옵션(자유 입력형)에 대해 노션 정책은 아래 허용/미허용 문자 규칙을 명시한다.

- **허용**: 한글·영어·한자·숫자 / 특수문자(`~ ! @ # $ % ^ & * ( ) / \ - [ ] _ + , . ? ' " ` : ; { } < >`) 및 띄어쓰기 / 도형기호(`☆ ★ ○ ● ◇ ◆ □ ■ △ ▲ ▽ ▼ ◁ ◀ ▷ ▶ ♤ ♠ ♡ ♥ ♧ ♣`)
- **미허용**: 위 도형기호 외의 특수문자, 이모지

이 문자셋 검증은 **be-api에 해당 로직이 없다** — 서버가 강제하지 않으며, **프론트 단독 검증으로 확정됐다(fe 코드 확인 2026-07-13)**: fe 후원 폼의 옵션 입력(`Textarea` 공용 컴포넌트 → `RewardItemOptions`·후원 옵션 변경 모달)이 위 허용 문자와 동일한 화이트리스트 정규식(`VALID_INPUT_FOR_REWARD_TEXT_OPTION` — 한글·영문·한자·숫자·지정 특수문자·도형기호 허용, 이모지 배제)으로 입력 문자를 즉시 제거한다. 선물 설명 필드에 적용되는 이모지 금지 검증은 옵션 값에는 적용되지 않는다.

## 한정 수량 차감·복구 & 동시성 제어

**1) 주 동시성 가드 — Redis 원자 연산**
- 선물별 카운터 키에 현재 후원 수량을 저장하며, TTL은 180일이다.
- 후원 요청 시 "현재 수량 + 요청 수량이 한도를 초과하는지"를 원자적으로 체크한 뒤 초과하지 않으면 카운터를 갱신한다. 카운터 키가 아직 없으면 DB의 결제 진행중 상태 카운트로 키를 재생성한 뒤 1회 재시도한다.
- 한도 초과 시 "선물 소진"(`END_REWARD`, HTTP 409 CONFLICT) 오류로 처리된다.
- 후원 트랜잭션이 롤백되면 커밋 완료 후 콜백에서 Redis 카운터를 원복(차감)한다. 원복 실패 시 Slack 알림이 발송된다.
- 한정 수량이 없는(무제한) 선물은 트랜잭션 커밋 직전에 카운트를 반영하고, 후원 취소 시 커밋 직전에 차감한다.

**2) DB 이중 검증**
- 한정 수량이 설정된 선물에 대해서는 위 Redis 체크 후에도, 후원 생성 시점에 DB 집계로 "결제 진행중 상태 후원 수 + 이번 주문 수량"이 한도를 초과하는지 **추가로 재확인**한다. 초과 시 동일하게 선물 소진 오류.

**3) 표시/필터용 잔량 캐시 (비원자)**
- `ProjectLimitReward.remainQuantity`는 "한도 − 결제 진행중 상태 후원 수"를 주기적으로 재계산해 **마지막 값으로 덮어쓰는** 방식으로 갱신된다(원자적 감산이 아니다). 잔량이 0 이하가 되면 해당 캐시 행은 삭제된다.
- 코드 주석에 "원래는 원자적으로 처리해야 하나 현실적 문제로 배치를 통해 주기적으로 데이터를 보정한다"는 설명이 명시되어 있다.
- 이 캐시는 프로젝트 목록·필터(잔여 수량이 있는 선물 중 최소 금액 조회 등)와 노출용으로만 쓰이며, 실제 판매 가부 판정의 SSOT는 위 1)·2)다.

**빈자리 알림**: 소진(품절)됐던 한정 선물에 취소·환불 등으로 다시 여유가 생기면 알림 대상이 된다.

## 알려진 정합성 리스크 (코드 내부 불일치 — 비즈니스 확인 대기)

1. **선물 한정 수량 상한 — API 세대별 병존**: 선물 생성·수정 API는 legacy 세대(`RewardItemController`/`RewardService`)와 v3 세대(`RewardItemV2Controller`/`RewardV2Service`/`StoreRewardService`)가 병존하며, 각 세대 내부는 생성·수정 상한이 일치한다 — legacy는 생성·수정 모두 1,000, v3는 생성·수정 모두 10,000. 노션 문서는 1,000(legacy 값)으로만 기재되어 v3 상향분을 반영하지 못하고 있다. 우려됐던 리스크는 클라이언트가 두 세대의 엔드포인트를 혼용해 호출하는 경우(예: v3로 1,001~10,000 생성 후 legacy 수정 시 검증 실패)였으나, **해소(fe 코드 확인 2026-07-13)**: 창작자 에디터(fe tumblbug-web `ProjectEditor`)는 선물 생성·수정 모두 v3 세대를 호출하며, legacy 엔드포인트는 선물 삭제·아이템 수정(수량 검증 무관)에만 사용됨이 확정됐다 — 혼용 검증 실패 리스크는 성립하지 않는다. 남은 것은 노션 기재값(1,000)이 v3 상향분(10,000)을 반영하지 못한 문서 스테일뿐이다.
2. **한정 수량 계산에 사용하는 결제 상태 범위 불일치**: 위 "DB 이중 검증"에서 사용하는 결제 상태 범위와, "표시용 잔량 캐시" 재계산에 사용하는 결제 상태 범위가 서로 다르다(전자는 취소·환불 관련 상태를 포함해 더 넓게 잡고, 후자는 결제 진행중/완료 상태만 좁게 잡는다). 이로 인해 환불된 슬롯이 잔량 캐시·Redis 카운터에서는 재개방된 것으로 보여도, DB 이중 검증에서는 여전히 소진 처리되어 선물 소진 오류가 오발생할 수 있는 케이스가 있다(코드에 TODO로 명시된 알려진 갭). 노션 정책에는 없는 구현 상세이며, 실제 영향 범위(프리오더 등 특수 결제 흐름 포함 여부)는 비즈니스·엔지니어링 확인이 필요하다.

## 디지털 에셋 / 디지털 선물

디지털선물은 파일 또는 텍스트 형태로 후원자에게 전달하는 비실물 선물 기능이며, 창작자의 에디터 화면에서 관리한다.

- **요금제 제약**: Run/Boost 요금제 창작자만 사용 가능. START 요금제에서는 사용할 수 없다("RUN, BOOST 전용 기능입니다" 안내).
- **유형별 제한**: 디지털선물 1개당 파일 또는 텍스트 중 1개만 등록 가능.
  - 파일: 지정된 확장자만 허용(아래 「허용 확장자」 참조), 1개당 최대 5GB, 프로젝트당 파일 총합 최대 100GB, 보관 기간은 등록일로부터 최대 1년, 다운로드 유효기간도 최대 1년.
  - 텍스트: 최대 300자, 복사 유효기간 최대 1년.
  - 디지털선물 이름: 최대 50자.
  - 유효기간 기본값(별도 지정하지 않은 경우): 등록일 + 1년(종일 단위 처리). 상시 프로젝트(즉시결제형)에서는 유효기간이 없다(무기한).
- **`RewardDigitalProfile.expiresInDays`(기본값 90)는 현재 실제 유효기간 계산에 쓰이지 않는 미사용 필드다.** 상시 프로젝트 즉시전달 디지털선물의 실제 유효기간은 `ImmediateDigitalAssetDeliveryService`의 별도 상수 `DEFAULT_EXPIRES_IN_DAYS=90`으로 계산되며, 코드 주석은 `RewardDigitalProfile`이 향후 "유효기간 개별 변경" 기능을 위해 예약된 미구현 필드임을 명시한다.

### 전달 상태 (창작자 화면 기준 — 상태머신)

| 상태 | 설명 |
|---|---|
| 전달 전 | 최초 생성 상태. 이 상태에서만 삭제 가능 |
| 전달 중 | 전달 처리가 진행 중인 상태 (실패해도 후원자에게는 "전달 중"으로 노출됨) |
| 전달 완료 | 전달 완료. 파일/텍스트 변경 시에도 이미 전달된 후원자에게 변경본이 반영되고 알림톡 발송 |
| 전체 회수 | 창작자가 전체 회수 처리. 후원자는 이후 다운로드/복사 불가. 삭제 불가 |
| 기간 만료 | 유효기간 경과로 배치가 자동 전이시킨 상태 |

- **초기 상태 분기**: 기간 펀딩(예약결제) 프로젝트는 "전달 전" 상태로 생성되지만, **상시 프로젝트(즉시결제형)는 생성 즉시 "전달 완료" 상태**로 생성된다(즉시 전달, 유효기간 없음).
- **후원자 화면 노출 상태**: 전달 중 / 전달 완료 / 전달 회수 / 기간 만료. 별도로 **확인 상태**(확인 이전 / 확인 완료)를 가지며, 확인 완료는 파일은 다운로드 클릭, 텍스트는 복사 클릭 시점에 기록된다.
- **전달 조건**: 프로젝트가 "성공" 상태로 확정된 이후에만 전달 가능("프로젝트가 성공한 이후에 전달 가능합니다" 안내). 창작자가 일괄 처리를 위해 체크박스로 선택할 수 있는 대상은 "전달 전" 상태인 "파일" 타입만.
- **전달 방식**: 파일은 선물 단위 선택(결제 완료된 후원자 대상) 또는 후원번호 CSV 업로드 중 선택. 텍스트는 CSV 업로드(후원번호별 매핑)만 지원. CSV에 유효하지 않은 후원번호가 포함되면 전달 자체가 불가능하다.
- **변경**: 파일/텍스트 내용 변경은 "전달 중" 또는 "전달 완료" 상태에서만 가능(회수·만료 상태는 변경 메뉴 자체가 노출되지 않음). 변경 시 이미 전달받은 후원자에게도 변경본이 반영되며 알림톡이 발송된다. 유효기간 변경은 등록일 + 최대 1년 범위 내에서만 가능하고, 이미 전달 완료된 건은 기존 만료일 이후로만 연장 가능.
- **회수/삭제**: 전체 회수 시 후원자는 다운로드/복사가 불가능해진다. 전달완료·전체회수 상태의 디지털선물은 **삭제할 수 없다**("전달 전" 상태만 삭제 가능 — 위 상태 표와 일치).
- **알림 채널**: 전달완료·파일변경·유효기간임박 발생 시 알림톡·시스템알림은 발송되지만, 앱푸시·메일은 발송되지 않는다.
- **만료 처리(배치)**: 유효기간이 지난 "전달완료" 상태 건을 배치가 주기적으로 "기간만료" 상태로 자동 전이시킨다.
- **전달 대상 관리**: 전달 대상은 선물 단위 또는 후원번호 CSV 단위로 지정되며, 후원자별 실제 지급 인스턴스는 별도로 관리되고 각 인스턴스가 개별 유효기간을 가진다.

### 허용 확장자 (요약)

파일 업로드 시 허용되는 확장자는 분류별로 지정되어 있다(하위 노션 페이지 기준, 전수는 90여 종). 대표 예시:

| 분류 | 확장자 예시 |
|---|---|
| 문서 | doc, docx, epub, hwp, idml, indd, pdf, ppt, pptx, txt, xls, xlsx |
| 동영상 | avi, mov, mp4, wmv |
| 사운드 | flac, m4a, mp3, wav |
| 폰트 | otf, ttf |
| 압축/패키지 | (분류만 존재, 개별 확장자는 노션 하위 목록 참조) |
| 이미지 & 그래픽 | (분류만 존재, 개별 확장자는 노션 하위 목록 참조) |
| 디지털아트 & 게임 & 기타 | (분류만 존재, 개별 확장자는 노션 하위 목록 참조) |

전수 목록은 위 「디지털선물 관리 기능(에디터)」 노션 페이지의 하위 페이지("디지털 에셋 허용 확장자 목록")에서 관리되며, 프론트 코드에도 별도 허용 확장자 목록이 있다(주석상 "추후 백엔드 API로 교체 예정" — 즉 현재는 프론트에 하드코딩되어 노션과 별개로 유지되는 상태로 추정, fe 워킹트리 미설정으로 코드 미확인).
