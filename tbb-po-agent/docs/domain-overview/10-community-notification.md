**작성 조건 상태값 상세 (A/A-1/B/C/D, 전체 값)**

- **A** (창작자 업데이트: 후원자 공개 작성 가능 조건) — 프로젝트 state ∈ {ongoing_not_reached(진행중_목표미도달), ongoing_reached(진행중_목표도달), cancelled(펀딩중단), failed(펀딩무산), succeeded_not_balanced(펀딩성공_미정산), succeeded_balanced(펀딩성공_정산완료)} AND public_state = 1(공개). 프로젝트 state 값은 `[03-project.md 참조]`(코드 미검증, 재인용).
- **A-1** (창작자 업데이트: 전체공개 작성 가능 조건) — A의 state 목록 + **prelaunched(공개예정)** 추가, public_state = 1(공개)
- **B** (후기 작성 가능 프로젝트 조건) — 프로젝트 state ∈ {succeeded_not_balanced, succeeded_balanced} (public_state 고려 안 함)
- **C** (후원자 후기 작성 가능 조건) — 후원 state = 2(PAID, 결제 완료)
- **D** (후원자 커뮤니티 글/댓글 작성 가능 조건) — 후원 state ∈ {0(PLEDGED, 결제 예약), 2(PAID, 결제 완료), 3(UNPAID, 결제 재시도 중), 5(CHARGING, 결제 대기), 6(PLEDGED_NOT_CHARGED — 프로젝트 무산으로 인한 미청구 취소; `PaymentState.CANCELLED`가 포함하는 `ProjectWarrantyState` 세부값, `[05-funding-payment.md 참조]`)}. **제외**: 1(CANCELLED, 결제 예약 취소), 4(DROPPED, 결제 누락)

**예외 (공개예정 상태 업데이트 댓글)**

- 프로젝트 공개예정 중: 알림신청자만 댓글 작성/삭제 가능
- 프로젝트 진행 중: 과거 알림신청자 + 후원자 댓글 작성/삭제 가능

### A-4. UGC 신고 · 자동 블라인드

- 신고 방법: 블라인드 처리된 게시글/댓글은 신고 불가
- 게시 불가 콘텐츠 자체를 정의하는 필터 정책은 별도 노션 페이지에 있으며 이번 분석 범위 밖이다.
- **자동 블라인드(숨김) 처리 로직 — 코드 실동작 기준**:
  - `ContentReportManagementStatus` 전체 값: `REVIEW_NEEDED`(검토필요), `NO_ACTION`(조치없음), `UNHIDDEN`(숨김해제), `VALID`(유효), `HIDDEN`(숨김), `AUTO_HIDDEN`(자동숨김), `DELETED`(삭제)
  - 신규 신고 접수 시 최초 생성 컨텐츠는 `status = REVIEW_NEEDED`로 시작
  - `REVIEW_NEEDED` 상태 유지 중 신규 신고가 들어올 때마다 `accumulatedCountInReview` +1 증가. 다른 상태에서 `REVIEW_NEEDED`로 되돌아가면(무효 처리 후 재신고 등) 1로 초기화
  - 자동 숨김 판정: `REVIEW_NEEDED` 상태 && `accumulatedCountInReview >= AUTO_HIDE_THRESHOLD - 1(=5)` — 이 판정은 "이번 신고 반영 전" 값 기준이므로, 실질적으로 **`REVIEW_NEEDED` 상태 진입 후 신규 신고 누적 6건째**에 자동 숨김(`AUTO_HIDDEN`)으로 전이한다. 상수: `AUTO_HIDE_THRESHOLD = 6`.
  - **노션 문서는 "누적 신고 3회"로 기재(코드 기준 실질 6건째)** — 코드 실동작이 SSOT. 상세는 아래 「노션↔코드 불일치」 참조.
- 숨김/삭제글 UX 노출 문구: "신고 접수 또는 운영정책 위반으로 숨김처리(또는 삭제조치)된 게시물입니다."
  - 타인 작성 글: 위 문구를 BE가 API로 서버에서 내려줌
  - 본인 작성 글: 위 문구 + 실제 본문(클라이언트에서 고정 문구로 노출)

### A-5. 메시지 차단 (창작자 ↔ 후원자)

메시지 차단 **불가** 조건 — 아래 2가지를 **모두** 충족할 경우 차단 불가:

1. 해당 창작자의 프로젝트에 대해 후원 이력이 있고, 후원 state ∈ {0(결제예약/PLEDGED), 2(결제완료/PAID), 3(결제재시도중/UNPAID), 5(결제대기/CHARGING)}
2. 선물 예상 수령일이 아직 경과하지 않음(후원한 선물 중 가장 늦은 예상 전달일 기준)

그 외의 경우(위 2조건 미충족)는 메시지 차단이 가능하다. 위 후원 state 라벨은 코드 `PaymentState` enum과 대조 완료 — 정합.

## B. 알림

### B-1. 알림 수신매체별 서비스 내 설정 항목

**이메일 알림 설정 (웹앱 공통)**: 메시지 / 프로젝트 업데이트 / 알림신청 프로젝트 / 좋아한 프로젝트 / 팔로우 / 마케팅

**푸시 알림 설정 (앱 전용, 전체)**:

1. 후원한 프로젝트 업데이트 알림(+이메일 switch)
2. 알림신청 프로젝트 업데이트 알림
3. 좋아한 프로젝트 업데이트 알림
4. 메시지 알림(+이메일)
5. 알림신청 프로젝트 공개(+이메일 switch)
6. 좋아한 프로젝트 마감(+이메일 switch)
7. 팔로우한 창작자 프로젝트 공개(+이메일 switch)
8. 키워드 푸시
9. 카테고리 푸시
10. 커뮤니티 댓글
11. 팔로우
12. 내 후기 창작자 댓글
13. 내 글 좋아요
14. 응원권 알림
15. 마케팅 알림(+이메일 switch)
16. 커뮤니티 게시글 [창작자 전용 알림]
17. 후원자 후기 작성 [창작자 전용 알림]

설정 해제 시 해당 수신매체로는 미발송되나 **서비스 내 알림 피드에는 계속 쌓인다**. 마케팅 알림 제외 전 항목 초기 상태는 **수신 ON**이다.

### B-2. 발송 매체 우선순위 및 원칙

- 모바일 알림 우선순위: **푸시 > 알림톡/문자**
  - 앱 설치자 → 푸시만 발송
  - 앱 미설치자 → 알림톡/문자 발송
  - (예외) 반드시 받아야 하는 알림은 **알림톡으로만** 발송
- 앱의 마케팅 푸시 설정값 = **앱 설치 시 설정한 값**을 따름
- 웹의 마케팅 이메일 알림값 = **회원가입 시 설정한 값**을 따름

### B-3. 발송 시간(야간 지연) 정책

- 사용자 행동 기반 알림은 **야간 발송 지연** 적용
- 오후 9시(21:00) 이후 ~ 익일 오전 7시 59분 이전 발생한 알림은 **다음날 오전 8시 일괄 발송**
- 매체별 적용 현황: 알림톡은 **우선 적용**(적용 완료), 이메일은 **해당 없음**(야간 지연 미적용), 푸시는 **VOC 확인 후 적용 준비**(노션 문구상 미확정 상태 — 아래 「[확인 필요]」 참조)
- 야간 지연 대상 알림 예시(전체): 알림신청 프로젝트 공개 / 배송 업데이트 / 배송 정보 마감 / 창작자 메시지 수신(후원자 관리에서 발송)

### B-4. 앱 알림 숫자(뱃지) 표시 정책

- 목적: 유저가 확인해야 할 정보 누락 방지 + 앱 방문 리텐션 확보
- 카운트 규칙: `{신규 발생한 알림수} + {안 읽은 메시지 수}`. 앱 접속 시 위 값으로 업데이트
- 제거 규칙:
  - 알림 탭 진입 시 → {신규 발생한 알림수} 카운트 제거
  - 메시지 쓰레드 확인 시 → 확인한 쓰레드의 메시지 카운트만 제거

### B-7. 창작자 업데이트 알림 발송 파이프라인 — 코드 실동작 (2026-07-16 확정)

> 2026-07-16 푸시 VOC 분석(알림 설정 해제에도 홍보성 업데이트가 피드 노출·푸시 수신된다는 후원자 불편)으로 코드 확정한 사실. 코드 경로(file:line)는 `docs/code-map.md` 섹션 10에 등재.

- **알림 타입 체계**: 서버 알림 타입(`NotificationType`)은 62종이며, 창작자 업데이트 관련은 3종 — 후원한 프로젝트 업데이트(`PROJECT_UPDATE_NOTI`) / 알림신청 프로젝트 업데이트(`PROJECT_PRELAUNCH_UPDATE_NOTI`) / 좋아한 프로젝트 업데이트(`PROJECT_LIKE_UPDATE_NOTI`) — 로 분리되어 B-1 푸시 설정 1·2·3번 토글과 1:1 대응한다. 푸시 수신설정 타입(v3 `PushNotificationType`)은 30종이고, 이 중 `ALWAYS` 타입은 수신 설정과 무관하게 항상 발송된다(시스템성 알림용).
- **설정 저장 모델**: 유저 푸시 설정은 `user_push_settings`(토글 28컬럼)에 저장. DB 기본값은 전 컬럼 ON이며 럭키드로우 신규회차(`luckyDrawNewRound`)만 기본 OFF다. 마케팅 항목의 실질 초기값은 B-2의 동의 플로우(앱 설치 시 설정값)가 결정한다.
- **푸시 발송 설정 게이트(be-api v2)**: 시스템 푸시 발송 시 설정 검증(`validatePushType`)은 ① 후원한 프로젝트 업데이트 = 푸시 설정 ON **AND** 이메일 뮤트 아님의 이중 조건 ② 알림신청·좋아요 업데이트 = 해당 푸시 설정 단일 조건 ③ `ALWAYS`·타입 미지정(null) = 무조건 통과로 분기한다.
- **알림 피드 적재는 설정과 무관 — 의도된 정책(코드 확정)**: 피드(알림 목록) 적재 로직은 수신 설정을 참조하지 않고 무조건 저장한다(예: 마감 프로젝트 성사/무산 알림 배치). B-1의 "설정 해제 시에도 서비스 내 알림 피드에는 계속 쌓인다" 정책 서술과 정합 — VOC 클레임 중 "피드 노출"은 버그가 아니라 정책이다.
- **업데이트 발행→실발송의 주체는 be-api-legacy(Ruby)**: 업데이트 글 발행 시 be-api(v2 Java)는 Ruby `delayed_jobs` 큐에 알림·메일 작업을 적재할 뿐, 업데이트 알림 3종을 실제 발송하는 v2 코드는 없다. 실제 팬아웃(대상 선정·중복 제거·피드 적재·설정 타입 지정)은 be-api-legacy(Ruby, 로컬 클론 제외 repo) 소관 — **코드 미검증**. 과거 Ruby 측 push_setting_type 오지정(설정 우회 발송) 버그 이력이 v2 주석으로 남아 있어, VOC 클레임 중 "설정 해제에도 푸시 수신"의 최종 판정은 Ruby 검증 전까지 미확정이다(아래 「[확인 필요]」 5번).
- **발송 빈도 제한 부재 확정**: 수신자 기준 발송 스로틀(쿨다운·일일 상한·묶음 발송)은 전 repo 부재 확정. 작성단 제한만 존재 — 업데이트 글 작성 rate limit **3회/1시간**(프로젝트+유저 키, `POST_WRITING`)이 **v3 API에만 적용**되고 레거시 작성 API에는 미적용(우회 구멍). 업데이트 글의 유형 분류축(홍보성 vs 이행·배송성)도 없다 — Post 유형(`PostType`)은 작성 맥락 구분(DEFAULT/SUPPORT/PREPARATION/PROJECT_PROGRESS)뿐이고, 공개범위(`PostVisibleType`)는 전체공개/후원자공개 2종뿐이다.

## 노션↔코드 불일치

1. **[핵심] UGC 자동 블라인드(숨김) 임계값 — 노션 "누적 신고 3회" vs 코드 실질 6건째**: 노션(UGC 신고 페이지 "자동 블라인드 처리 로직")은 "누적 신고 3회"로만 기술하나, 코드 실동작(`AUTO_HIDE_THRESHOLD = 6`, 판정은 "반영 전" 값 기준)은 `REVIEW_NEEDED` 진입 후 신규 신고 6건째에 자동 숨김된다. 두 값은 2배 차이이며 같은 개념(신고 건수 임계값)을 가리키는 것으로 보인다. 코드 실동작 우선 원칙에 따라 코드(6)가 SSOT이며, 노션 페이지 정정이 권고된다.
2. **후원 state 5번 라벨 표기 차이(실질 불일치 아님)**: UCC 페이지는 영문 코드명 `5(charging)`, 메시지차단 페이지는 한글 `5(결제대기)`로 표기하나 코드 확인 결과 동일 상태(`CHARGING`, "결제 대기")를 가리키며 값 자체는 정합한다. 이 문서는 A-2·A-5에서 통일 표기(`CHARGING`, 결제 대기)로 반영했다.
3. **UCC 페이지 "6(pledged_not_charged)"는 `PaymentState` 자체 값이 아니라 하위 세부상태**: `PaymentState.CANCELLED`가 포함하는 `ProjectWarrantyState.PLEDGED_NOT_CHARGED`(`05-funding-payment.md` 소관)다. 값 자체(포함 여부)는 정합이나 상태 체계 레이어가 노션 문서상 구분되지 않아, 이 문서 A-2에서 각주로 명시했다.

## [확인 필요]

1. **푸시 야간 발송 지연 실제 적용 여부** — 노션이 "VOC 확인 후 적용 준비"로 자체 미확정 표기. 현재 실제로 적용됐는지는 운영/PM 확인이 필요하다.
2. **UGC 신고 접수 채널의 현재 상태** — 노션 UGC 신고 페이지의 "아카이빙(이전 히스토리)" 섹션은 Tally 폼 기반 수동 수집 프로세스를 기술하나, 코드에는 인앱 신고 처리 시스템(`ContentReportManagement` 등)이 이미 구현되어 있다. Tally 프로세스가 완전히 폐기됐는지, 특정 유형(예: 메시지 신고)에 한해 잔존하는지는 운영 프로세스 확인이 필요하다.
3. **메시지 차단 매커니즘 자체의 문서화 공백** — 노션 "메시지 차단 기능" 페이지의 "메시지 차단" 섹션 본문이 비어 있어 차단 트리거 UI·차단 시 상대 안내 여부 등 차단 불가 조건 외의 핵심 스펙이 문서에 없다. 기획/디자인 쪽 원 스펙(Figma 등) 확인이 필요하다.
4. **알림별 발송매체 매핑 원본(구글 스프레드시트)** — 노션 페이지에 임베드된 시트 링크는 외부 파일이라 열람 불가했다. 매체별(이메일/푸시/알림톡/문자) 상세 매핑표는 시트 원본 확인이 필요하다.
5. **창작자 업데이트 알림 실발송 로직(be-api-legacy Ruby) 미검증** — 업데이트 알림 3종의 실제 팬아웃(대상 선정·중복 제거·피드 적재·설정 타입 지정)은 be-api-legacy(Ruby) 소관인데 로컬 클론 제외 repo라 코드 미검증(B-7 참조). 과거 push_setting_type 오지정 버그 이력(v2 주석)이 있어, "설정 해제에도 푸시 수신" VOC의 최종 판정(설정 우회 경로 존부)은 Ruby 코드 확인이 필요하다. (백로그 B-42)
