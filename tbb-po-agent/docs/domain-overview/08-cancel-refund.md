## 취소 성격 구분 (CANCEL vs REFUND)

후원 1건의 취소·환불 요청은 결제 시점을 기준으로 두 성격으로 나뉜다(`ProjectWarrantyCancelType`, 2종).

| 코드명 | 한글 라벨 | 의미 |
|---|---|---|
| `CANCEL` | 취소(미결제) | 결제 전 후원 취소. 창작자 승인 없이 **자동 승인**된다 |
| `REFUND` | 환불(결제후) | 결제 이후 취소. **창작자의 승인이 필요**하다(기한 초과 시 배치가 자동 승인) |

## 취소·환불 관련 Enum

### 처리 상태 (`ProjectWarrantyCancelStatus`, 3종)

취소 건(`CANCEL`)과 환불 건(`REFUND`)은 같은 상태 Enum을 공유하지만 화면 라벨이 다르다.

| 코드명 | 취소용 라벨 | 환불용 라벨 |
|---|---|---|
| `REQUESTED` | 취소 요청 | 환불 요청 |
| `REJECTED` | 취소 거부(코드 라벨 원문에 오타 있음) | 환불 거부 |
| `APPROVED` | 취소 승인 | 환불 승인 |

### 사유 (`ProjectWarrantyCancelReasonType`, 4종 + 노출범위 2버킷)

| 코드명 | 한글 라벨 |
|---|---|
| `CHANGE_OF_MIND` | 단순 변심 |
| `ORDER_MISTAKE` | 주문 실수 |
| `DAMAGE_AND_DEFECT` | 파손 및 불량 |
| `MISDELIVERY_AND_MISSING_PARTS` | 오배송 / 구성품 누락 |

- `BEFORE_DELIVERY` = {단순 변심, 주문 실수} — **선물 전달 전** 또는 **상시 프로젝트**면 이 2종만 노출된다.
- `AFTER_DELIVERY` = {4종 전부} — 선물 전달이 완료된 펀딩/프리오더 후원은 파손·오배송 사유가 추가로 노출된다.
- 성공한 프로젝트의 후원을 취소할 때는 사유가 필수이며, 상세 사유는 최소 10자 이상이어야 통과된다.

### 후원 최종 결과 타입 (`FundType`, 5종)

| 코드명 | value | 한글 라벨 |
|---|---|---|
| `PLEDGED` | pledged | 결제 예약 |
| `PAID` | paid | 결제 완료 |
| `DROPPED` | dropped | 결제 누락 |
| `REFUNDED` | refunded | 환불 완료 |
| `PLEDGED_NOT_CHARGED` | pledged_not_charged | 결제 전 취소(프리오더 성사 후 결제 전 취소) |

## 후원(ProjectWarranty) 상태 중 취소·환불 관련 값

전체 12개 후원 상태와 펀딩 결제 흐름 일반은 `[05-funding-payment.md 참조]`. 아래는 그중 취소·환불에 직접 관련된 값만 재정리한 것이다.

| value | 코드명 | title(기본) | 펀딩 라벨 | 취소·환불 의미 |
|---|---|---|---|---|
| 1 | `CANCELLED` | 밀어주기 취소 | 후원 취소 | 진행중 미결제 취소 / 상시 결제취소의 종착 상태 |
| 4 | `DROPPED` | 결제 누락 | 결제 최종 실패 | 7일 청구 실패 최종 상태(미청구분, 환불 아님) |
| 6 | `PLEDGED_NOT_CHARGED` | 결제 예약 취소 | 후원 취소 | 프리오더 성사 후 결제 전 취소(자동 승인) |
| 7 | `REFUND_REQUESTED` | 환불 요청중 | 환불 요청중 | 결제 후 환불 요청, 창작자 승인 대기 |
| 8 | `REFUND_REJECTED` | 환불 거절 | 환불 불가 | 창작자가 환불 요청을 거절 |
| 9 | `REFUND_PROCESSING` | 환불중 | 환불 완료 | 환불 승인 후 PG 환불 진행 중 |
| 10 | `REFUNDED` | 환불 완료 | 환불 완료 | 환불 확정 |

**취소·환불 관련 상태 버킷**:

| 버킷 | 포함 상태 | 의미 |
|---|---|---|
| `CANCELLED_STATES` / `PAYMENT_CANCELLED_STATES` | CANCELLED, DROPPED, PLEDGED_NOT_CHARGED | 취소·결제취소 상태 그룹(두 버킷은 동일 집합) |
| `PAYMENT_REFUNDED_STATES` | REFUND_PROCESSING, REFUNDED | 환불 확정 판정(`isRefunded()`) 기준 |
| `BACKING_FAILED_STATES` | CANCELLED, DROPPED, PLEDGED_NOT_CHARGED, REFUND_PROCESSING, REFUNDED | 후원 실패로 집계되는 상태 전체 |
| `CANCEL_STATES`(엔티티측) | CANCELLED, DROPPED, PLEDGED_NOT_CHARGED | 엔티티가 판정하는 취소 상태 |

> `PAYMENT_SUCCESS_STATES`에는 REFUND_REQUESTED·REFUND_REJECTED도 포함된다(`[05-funding-payment.md 참조]`). 즉 **환불 요청/거절 중이어도 "결제됨"으로 집계**되며, 환불이 실패 집계로 잡히는 시점은 REFUND_PROCESSING·REFUNDED부터다.

## 취소·환불 상태 전이

| 이벤트 | from → to | 트리거 |
|---|---|---|
| `MARK_AS_CANCELLED` | PLEDGED → CANCELLED | 기간펀딩 진행중 후원 취소 |
| `REPLEDGE` | CANCELLED → PLEDGED | 취소 후 재후원 |
| `FORCE_NOT_CHARGE` | (제한 없음) → PLEDGED_NOT_CHARGED | 강제 미청구 처리 |
| `STORE_BACKING_CANCEL` | PAID → CANCELLED | 상시 즉시결제 취소(전량 취소 시) |
| `BILLING_KEY_INIT_CANCEL` | INIT → CANCELLED | 빌링키 등록 중 선물 소진 등 실패 |
| `MARK_AS_REFUND_PROCESSING` | PAID / REFUND_REQUESTED → REFUND_PROCESSING | 프리오더 환불 승인(수동/배치 자동) |
| `MARK_AS_REFUNDED` | PAID / REFUND_PROCESSING → REFUNDED | PG 환불 확정 |

REFUND_REQUESTED·REFUND_REJECTED·PLEDGED_NOT_CHARGED 진입은 위 표의 선언적 이벤트가 아니라 서비스 로직이 상태를 직접 갱신하는 절차적 처리다 — `[05-funding-payment.md 참조]`에서 확인한 "선언적 상태머신 미구현" 특성이 취소·환불 경로에도 그대로 적용된다.

## 취소·환불 경로 (모델별 3계통)

### [A] 기간 펀딩(예약결제) 후원 취소

**A-1. 진행중 미결제 취소** — 후원자 본인이면서 프로젝트가 진행중일 때만 가능(마감되면 거부). 처리:
- PLEDGED → CANCELLED로 즉시 전이(자동 승인, 창작자 개입 없음)
- 결제수단 정리: 네이버페이는 정기결제 해지, IAMPORT는 빌링키 취소
- 선물 한정수량 복구(빈자리 알림 + 한정수량 롤백 + Redis 주문수 차감), 쿠폰 취소, 배송정보 삭제

**A-2. 결제 후 취소·환불 요청(프리오더 포함)** — 검증: 후원자 본인 + (진행중 또는 성공) + **성공 상태면 프리오더만 허용**(비프리오더 성공 건은 거부) + 취소 가능 조건 충족 + 성공 시 사유·상세사유(10자 이상) 필수. 분기:
  - **미결제 상태**: `CANCEL` 성격, 상태 `APPROVED`(자동 승인), PLEDGED_NOT_CHARGED로 즉시 전이
  - **결제된 상태**: `REFUND` 성격, 상태 `REQUESTED`, REFUND_REQUESTED로 전이 + 승인 기한 **오늘+7일** 설정 + 창작자에게 환불요청 알림톡 발송
  - 취소 가능 조건: PLEDGED 상태면 항상 가능. 프리오더는 미배송이면 가능하고, **배송 완료된 경우 전달완료일+7일 이내에만** 가능하다.

### [B] 프리오더 환불 승인/거절/연장 (창작자·운영)

- **승인**: 프리오더 + REFUND 성격 + REQUESTED 상태 + 기한 이내인 건만 승인 가능하며, 동시 승인 요청에 대비해 대상 레코드를 조회 시점에 직렬화(락)한다. 승인되면 취소건은 REQUESTED→APPROVED, 후원은 REFUND_REQUESTED→REFUND_PROCESSING으로 전이한 뒤 결제수단별로 환불을 실행한다.
  - **계좌(BANK_ACCOUNT)**: 자동화 없이 운영셀 Slack 알림만 발송 — **수동 환불**
  - **IAMPORT**: 동기 처리로 즉시 REFUNDED까지 확정
  - **네이버페이·카드**: 비동기(레거시) 처리 경로로 위임
- **거절**: 프리오더 + REFUND 성격 + REQUESTED 상태 + 기한 이내 조건은 승인과 동일. 취소건은 REQUESTED→REJECTED, 후원은 REFUND_REQUESTED→REFUND_REJECTED로 전이한다.
- **기한 연장**: 승인 기한을 **+3일** 늘릴 수 있으나 **1회만** 가능하다(이미 연장했으면 거부).
- **자동 승인 배치**: 승인 기한이 지난 REQUESTED 상태 환불 건을 매일 **00:10**에 자동 승인·환불 처리한다(k8s CronJob). 건별로 독립 트랜잭션과 락을 사용해 중복 처리를 막는다. **자동 승인 대상 결제수단은 카드·네이버페이·IAMPORT뿐이며, 계좌는 예외 처리되어 자동 승인에서 제외된다.**
- **Iamport 환불 실행**: 결제 전액을 취소(부분 취소 아님)하고 REFUNDED로 확정한다. 환불 시 PG수수료도 음수 값으로 함께 기록된다. 환불 실행이 실패하면 예외를 삼키고 Slack으로만 알리며, 상위 트랜잭션의 REFUND_PROCESSING 전이는 그대로 커밋된다 — 이 경우 후속 처리는 수동 대응 대상이 된다.

### [C] 상시 프로젝트(즉시결제) 취소

- **부분/전체 취소 모두 지원**한다(기간 펀딩과 다른 점). 취소 대상 선물 ID를 지정하면 부분 취소, 지정하지 않으면 전체 취소로 처리된다.
- 디지털 에셋을 이미 다운로드한 경우 해당 단위(전체 취소면 후원 전체, 부분 취소면 해당 선물)는 취소가 차단된다.
- 후원의 상태 전이(PAID→CANCELLED)는 **포함된 모든 선물이 취소 완료됐을 때만** 일어난다. 부분 취소만으로는 후원 전체 상태가 바뀌지 않는다.
- PG 취소: 카드(NicePay)는 부분/전체 여부를 파라미터로 구분해 전달한다. IAMPORT는 부분 취소 시 결제 상태 자체는 갱신하지 않고(전체 취소만 결제 상태를 갱신), 취소 여부 플래그로만 구분한다.
- 상시 취소 시 한정수량 선물의 Redis 주문수 복구 로직이 현재 비활성화되어 있다 — 기간 펀딩 진행중 취소([A-1])는 복구가 활성인 것과 비대칭이다(아래 「[확인 필요]」 참조).

## 부분 취소 금액·수량 재계산

- **전체 취소**: 원래 결제 금액 전액을 반환하고, 후원 금액을 0으로, 선물 상태를 환불 완료로 변경한다.
- **부분 취소(선물 단위)**: 지정된 선물 중 **아직 취소되지 않은 선물만** 취소 대상이 되며, 그 선물들의 총액을 합산해 후원 금액에서 차감한다. 모든 선물이 취소되면 그 시점에 후원 전체가 환불 완료로 전이된다.
- **선물 단위 취소는 항상 전량 처리**된다 — 취소 시 해당 선물의 남은 수량 전부가 취소되고, 반환 금액은 "단가 × 수량"으로 계산된다.
- ⚠️ **갯수 단위 부분취소는 지원하지 않는다(확정)**: 같은 선물(옵션)을 구매한 수량 중 일부만 취소하는 것은 불가능하며, 취소 단위는 항상 "선물(옵션) 전량"이다. 기간 펀딩은 후원 전체 취소만 가능하고, 상시 프로젝트만 선물 단위 부분 취소를 지원한다.
- **취소 시 PG수수료 재계산은 원칙적으로 취소 서비스 책임 범위 밖**이다 — 부분 취소 시 PG에는 취소 금액만 전달되고, 취소분에 대한 PG수수료 재계산은 정산 단계에서 이뤄진다(`[06-settlement.md 참조]`). 예외적으로 프리오더 Iamport 환불 경로만 취소 시점에 음수 수수료를 함께 기록한다.

## 환불 수단·기한·PG 연동

| 항목 | 값·처리 |
|---|---|
| 창작자 환불 승인 기한 | 결제 후 환불 요청 시 **오늘+7일**(초과 시 배치가 자동 승인) |
| 기한 연장 | **+3일, 1회 한정** |
| 자동 승인 배치 | 매일 **00:10**, 대상 결제수단은 카드·네이버페이·IAMPORT만 |
| 카드 환불 | 프리오더는 레거시(Ruby) 비동기 처리 / 상시는 NicePay 취소 API |
| 네이버페이 환불 | 프리오더는 레거시(Ruby) 비동기 처리 / 진행중 취소는 정기결제 해지(expire) |
| 계좌(BANK_ACCOUNT) 환불 | **자동화 없음 → 운영셀 Slack 노티 후 수동 처리** |
| IAMPORT(카카오페이·토스페이 등) 환불 | 프리오더·상시 각각 별도 서비스가 동기로 처리 |
| NicePay 취소 파라미터 | 취소금액, 부분취소 여부 플래그, 취소 비밀번호 — 예외 발생 시 결과코드가 예외로 기록 |
| Iamport 취소 파라미터 | 취소금액, 결제총액(검증용), 전체취소 여부(`isAll` = 부분취소의 반대) |

지갑 크레딧(비즈머니) 환불(`CreditRefundService`)은 후원 취소·환불과 **별개 계통**이다(수수료 3%, 소수 첫째자리 올림 처리). 후원 도메인이 아니므로 상세는 `[11-adcenter.md 참조]`.

## 펀딩 실패·프로젝트 무산 시 환불

- **목표 미달(펀딩 실패)**: 예약결제 구조상 성공한 프로젝트의 후원만 청구 단계로 전이되며, **실패한 프로젝트는 청구 자체가 시작되지 않는다 → 환불 개념 자체가 없다(미청구)**. 불변식 "목표 미달 시 전액 미청구"의 코드 근거다(`[05-funding-payment.md 참조]`).
- **결제 누락(DROPPED)**: 7일간 청구를 재시도하고도 실패하면 최종적으로 이 상태가 되는데, 애초에 청구된 적이 없는 미청구분이므로 이 역시 환불이 아니다(`[05-funding-payment.md 참조]`).
- **성공 후 프로젝트 무산(비프리오더 기간 펀딩)**: be-api(api·admin·batch·core 전 모듈)에 성공한 후원 전체를 일괄 환불 처리하는 서비스나 배치가 **부재로 확정**됐다 — 환불로의 상태 전이를 일으키는 호출부는 위 [B] 프리오더 환불 경로 3곳뿐이다. 실제 처리 위치·프로세스는 아래 「[확인 필요]」 참조.
- **프리오더 개별 환불**: 위 [B] 경로로 처리된다(성공 후에도 후원자가 요청하면 창작자가 승인).
- ⚠️ **비프리오더 기간 펀딩은 성공(결제 완료) 후 후원자가 셀프로 취소·환불할 수 없다** — 검증 로직상 성공 상태에서는 프리오더만 취소·환불 요청이 허용되기 때문이다. 성공한 일반 펀딩의 환불은 후원자 셀프 경로가 코드에 없으며, CS/운영 개입으로 처리되는 것으로 추정된다.

## 노션 ↔ 코드 불일치

취소·환불 전용 노션 정책 페이지가 없어 대부분 "값 충돌"이 아니라 "노션 정책 문서 공백" 형태다. 아래 3건은 노션에 미기재(코드 기준 확정)된 사실이므로, 코드 실동작을 그대로 채택했다.

1. **환불 처리 기한·연장·자동승인** — 노션에 미기재(코드 기준 결제 후 환불 요청 시 7일 승인 기한 / +3일 1회 연장 / 기한 초과 시 매일 00:10 자동 승인 존재). 코드가 유일한 근거이므로 신규 문서화가 필요하다.
2. **계좌(BANK_ACCOUNT) 환불 수동 처리** — 노션에 미기재(코드 기준 자동 환불이 불가능해 운영셀 Slack 노티 후 수동으로 처리하며, 프리오더 자동 승인 배치에서도 계좌는 제외되어 있음). `[05-funding-payment.md 참조]`의 "계좌 청구 배치 부재"와 같은 맥락으로, 계좌 결제·환불이 be-api(Java)로 미이관된 상태다.
3. **부분 취소는 선물(옵션) 단위 전량만 가능** — 노션에 미기재(코드 기준 갯수 단위 부분 취소는 지원하지 않으며, 상시 프로젝트만 선물 단위 부분 취소를 지원하고 기간 펀딩은 후원 전체 취소만 가능함). 정책 문서화와 의도 확인이 모두 필요하다.

## `[확인 필요]`

1. **성공 후 프로젝트 무산(비프리오더 기간 펀딩) 시 후원 일괄 환불 경로** — be-api(api·admin·batch·core) 전 범위에서 부재가 확정됐다. 레거시(Ruby) 시스템에 남아 있는지, 어드민 수동 처리인지, 별도 운영 프로세스가 있는지는 엔지니어링/운영 확인이 필요하다.
2. **갯수 단위 부분취소 미지원이 의도된 정책인지** — 코드에는 향후 갯수 단위 부분 취소를 염두에 둔 주석이 남아 있다. 선물 옵션 수량 일부만 취소하려는 실제 니즈가 있는지는 프로덕트 의사결정 대상이다.
3. **상시 취소 시 한정수량 선물의 Redis 주문수 복구 비활성화 의도 여부** — 기간 펀딩 진행중 취소([A-1])는 복구가 활성인 것과 비대칭이다. 취소분이 재고로 돌아오지 않을 가능성이 있어 버그성으로 의심되며, 엔지니어 확인이 필요하다.
4. **계좌(효성) 환불 수동 Slack 처리의 유지/자동화 로드맵** — be-api(Java)로 미이관된 상태가 `[05-funding-payment.md 참조]`의 계좌 청구 잔존 이슈와 동일한 맥락이다. 이관 계획 여부는 결정 사항이다.
5. **프리오더 환불 승인 화면의 안내 문구와 실제 처리 로직 간 불일치** — **화면 위치·불일치 내용 확정(fe 코드 확인 2026-07-13)**: 화면은 fe-admin이 아니라 창작자 후원자 관리 콘솔(fe next-web `backer-manager`의 환불 승인 모달)이다. 안내 문구 "환불을 승인하면 즉시 후원자의 결제가 취소됩니다"는 계좌결제 건에 부정확하다 — 실제로는 승인 시 환불 처리중 상태로 전이한 뒤 계좌 건은 Slack 수동 처리를 대기한다(위 [B] 참조; 카드·간편결제 건만 즉시성에 가깝다). 문구 정정(결제수단별 처리 시점 안내) 실행 여부는 기획 결정 사항.
