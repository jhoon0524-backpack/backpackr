## 개요: 두 개의 독립된 정산 파이프라인

텀블벅 정산은 성격이 다른 두 개의 파이프라인으로 구현되어 있다.

| 구분 | 대상 | 실행 방식 |
|---|---|---|
| 펀딩/프리오더 정산 | 기간 펀딩 프로젝트(All-or-Nothing) 단위 | 정산일에 배치가 자동 실행 |
| 상시 프로젝트 정산 | 상시 판매 프로젝트, 월별·창작자별 집계 | 어드민이 데이터를 확정(FIXED)해야 송금까지 진행 |

노션 "창작자 정산"·"수수료 요금제 정책" 두 페이지는 **펀딩 정산 관점만** 다루고 있다. 상시 프로젝트 정산 파이프라인은 노션 문서에 없으며, 이 문서의 해당 섹션은 코드 기준으로 신규 정리한 것이다.

## 1. 수수료 요금제 (Rate Plan)

### 1-A. 요금제별 수수료율

> 대외 명칭 START/RUN/BOOST — 2026-07-09 PO 확인. 코드 Enum은 BASIC/PRO/PREMIUM 유지(매핑: BASIC→START, PRO→RUN, PREMIUM→BOOST).

| 대외 명칭 | 코드 Enum | 서비스 수수료율 | 결제 수수료율 |
|---|---|---|---|
| START | BASIC | 5% | 3% (요금제 무관 고정) |
| RUN | PRO | 9% | 3% |
| BOOST | PREMIUM | 15% | 3% |
| DEFAULT (폴백) | DEFAULT | 5% | 3% |

- 결제 수수료는 요금제와 관계없이 **3% 고정**이다. 펀딩·상시 두 파이프라인 모두 동일하게 적용된다.
- 상시 프로젝트를 신규 생성하면 기본 요금제는 **RUN(코드: PRO)**로 설정된다.

### 1-B. MOU 예외 요율

- 협약(MOU)을 맺은 창작자·프로젝트는 어드민에서 개별 요율(프로젝트 커미션)을 등록할 수 있다. 등록된 예외 요율은 창작자가 선택한 요금제 요율보다 **우선 적용**되며 정산 명세서에 자동 반영된다.
- 상시 정산에서 한 프로젝트에 예외 요율이 여러 개 걸려 있으면, 그중 **값이 가장 작은 요율**이 우선 적용된다.

### 1-C. 요금제별 부가 혜택 [확인 필요]

| 대외 명칭 | 코드 Enum | 제품 기능 | 광고 혜택 | 심사 |
|---|---|---|---|---|
| START | BASIC | 펀딩·공개예정·대시보드 일부 | 광고 신청 불가(2023 기재 — 최신 광고 수수료표에는 START 15% 요율이 존재해 상충, `[11-adcenter.md 참조]`) | 없음 |
| RUN | PRO | +대시보드 Full·응원권 발급 | SNS 광고 수수료 10% (구 기재 "SNS 광고 대행(수수료 면제)"는 스테일 판정) | 없음 |
| BOOST | PREMIUM | +대시보드 Full·응원권 발급 | SNS 광고 수수료 면제(0%)·커스텀 타겟 전용 + 옵션1 SNS 플러스 패키지(예산 150% 집행) 또는 옵션2 온드미디어(500만원 상당, 2023 기재) | 없음 |

이 표는 2023-09-12자 노션 문서 기준(구명칭 BASIC/PRO/PREMIUM 기재)에서 출발했으며 정산 코드 범위 밖(광고센터·마케팅 정책 소관)이다. 이후 두 차례 갱신됐다: ① BOOST 심사(퀄리티 스크리닝·반려)는 노션 원문에 있으나 **현행 심사 없음**(PO 확인 2026-07-09). ② **광고 혜택 열은 최신 SNS 셀프 광고 노션(2025-05-23)·코드 확정으로 정정**(PO 승인 2026-07-10) — SNS 광고 수수료율은 정산 수수료율과 별개 값으로, START 15% / RUN 10% / BOOST 0%(면제)이며 구 노션의 "RUN 수수료 면제"는 스테일 판정(상세는 `[11-adcenter.md 참조]`). 단 **SNS 셀프 광고 메뉴는 현재 제거되어 이용불가 상태**(PO 확인 2026-07-10). **[확인 필요]**: 제품 기능 혜택·BOOST 옵션 패키지·START 광고 신청 가능 여부의 현행성은 정책 오너/마케팅·운영셀 확인 대상.

### 1-D. 요금제 변경 프로세스 [확인 필요]

- 승인 전: 창작자가 직접 요금제를 변경할 수 있다.
- 승인 후: 헬프센터로 요청 → 운영셀이 어드민 권한으로 변경한다.

**[확인 필요]**: 위 변경 프로세스가 현행 운영 프로세스와 일치하는지는 운영셀 확인 대상(노션 문서 갱신일 2023-09-12로 오래됨).

## 2. 정산 계산식

### 2-A. 펀딩/프리오더 정산 계산식

상수: `VAT_RATE = 0.1`

```
창작자 정산금(toCreatorAmount)
  = 총 결제 보증금액(paidWarrantyAmount, = 프로젝트 총 모금액)
  − 텀블벅(서비스) 수수료
  − 결제 수수료
  − 예치 수수료
  − 위 3개 수수료의 부가세 합
  − 후불광고 차감액
  → 원 단위 절사(내림)

각 수수료의 부가세 = 수수료 × 10%, 원 단위 절사(내림)
```

- **정산 불가 조건**: 계산된 창작자 정산금이 0보다 작으면(모금액이 송금액+수수료 합보다 작으면) 해당 프로젝트는 정산이 중단된다.
- **후불광고 차감액**: 완료되었고 차감 대상으로 표시된 후불광고 집행분의 (공급가액 + 부가세) 합계. 없으면 0.
- 노션 문서는 정산 금액을 "(프로젝트 모금액) − (서비스 수수료 + VAT) − (결제 수수료 + VAT)"로만 기재한다(코드 기준은 여기에 예치 수수료와 후불광고 차감액도 추가로 차감한다. 예치 수수료는 현행 요율 체계에서 0원이라 실질 영향은 없지만, 후불광고 차감액은 실제로 차감이 발생한다).

**텀블벅 수익계좌 송금액**(창작자 정산금과는 별도 계산):

```
텀블벅 수익계좌 송금액 = 텀블벅(서비스) 수수료 + 그 부가세 + 후불광고 차감액
  → 원 단위 절사(내림)
```

- **결제 수수료는 텀블벅 수익계좌로 송금하지 않는다.** 창작자 정산금에서는 차감되지만, 텀블벅 송금액 계산에는 포함되지 않는다(2026-06-08 재무회계셀 결정). 노션 문서에는 이 자금 흐름 구분이 없다 — "창작자 정산금에서 차감되는 항목"과 "텀블벅이 실제로 수취하는 항목"은 다르다는 점을 정합성 확인 시 유의해야 한다.

**펀딩 수수료 산정** (현행 payoutVersion 6 기준):

| 수수료 | 계산식 | 반올림 |
|---|---|---|
| 텀블벅(서비스) 수수료 | 총 모금액 × 요금제 커미션율(MOU 예외 요율 우선) | 반올림 |
| 결제 수수료 | 총 모금액 × 3% | 반올림 |
| 예치 수수료 | 0 (payoutVersion 4 이상) | — |

**[확인 필요]**: 특정 레거시 프로젝트들에 대해 요율 계산 로직을 강제로 최신 버전(payoutVersion 6)으로 고정하거나, 개별 프로젝트 1건에 한해 별도 계산식(모금액 × 3%)을 적용하는 하드코딩 예외가 코드에 존재한다. 이 예외 처리의 정책적 근거·문서화 여부는 재무/정산 담당 확인 대상.

### 2-B. 상시 프로젝트 정산 계산식 (건별)

```
정산 대상 판정 기준일 = min(구매확정일, 결제일 + 7일)   [환불 가능 기간 7일]

선물 금액     = 단가 × 수량
응원권 차감액 = 응원권 비례 배분
결제 반영 금액 = 선물 금액 − 응원권 차감액
수수료율      = MOU 예외 요율(있으면 그 값) 또는 요금제 수수료율(%)

서비스 수수료      = 결제 반영 금액 × (수수료율 × 0.01),  원 단위 반올림
서비스 수수료 부가세 = 서비스 수수료 × 10%,                원 단위 절사(내림)
결제 수수료율      = 3% (고정)
결제 수수료        = 결제 반영 금액 × 3%,                  원 단위 반올림
결제 수수료 부가세  = 결제 수수료 × 10%,                    원 단위 절사(내림)

정산 금액 = 선물 금액 − 응원권 차감액
          − 서비스 수수료 − 서비스 수수료 부가세
          − 결제 수수료 − 결제 수수료 부가세
```

- 상시 정산 대상 기준: "결제일 + 7일" 또는 "구매확정일" 중 **더 이른 날짜**가 정산 대상월에 속하면 해당 건이 그달 정산 대상이 된다.
- 창작자별·월별 최종 정산 금액은 이 건별 정산 금액을 모두 합산한 값이다.

### 2-C. 반올림 모드 비교 (모델별 상이 — 정합성 주의)

| 모델 | 수수료 자체 | 수수료 부가세 | 최종 정산금 |
|---|---|---|---|
| 펀딩/프리오더 | 반올림 | 절사(내림) | 절사(내림) |
| 상시 프로젝트 | 반올림 | 절사(내림) | (건별 계산식에 이미 반영, 별도 절사 없음) |

두 모델 모두 문서화된 적이 없던 부분이며, 반올림 모드가 원 단위 손익에 직접 영향을 주므로 정합성 점검 시 반드시 모델을 구분해서 확인해야 한다.

## 3. 정산 상태 (State Machine)

### 3-A. 펀딩 프로젝트 정산 관련 상태

프로젝트 상태(전체 다수 상태 중 정산 관련 2종만 발췌):

| 상태값 | 한글 라벨 | 의미 |
|---|---|---|
| `SUCCEEDED_NOT_BALANCED` | 성공 | 펀딩 목표 달성·성공했으나 아직 정산 전 |
| `SUCCEEDED_BALANCED` | 성공/정산완료 | 정산까지 완료됨 |

- **멱등성 불변식**: 정산완료 상태로의 전이는 현재 상태가 `SUCCEEDED_NOT_BALANCED`일 때만 허용되고, 그 외 상태에서 시도하면 예외가 발생한다. 이 규칙으로 중복 정산(같은 프로젝트가 두 번 정산되는 상황)을 막는다.

### 3-B. 창작자향 정산 상태 표시

창작자가 보는 정산 진행 상태(`PayoutStatus`, 5종):

| 상태값 | 한글 라벨 |
|---|---|
| `PAYMENT_IN_PROGRESS` | 결제기간 |
| `UNSETTLED` | 정산 미확정 |
| `PAYOUT_CONFIRMED` | 정산 확정 |
| `FIRST_PAYOUT_COMPLETED` | 첫 정산 완료 |
| `PAYOUT_COMPLETED` | 정산 완료 |

정산 지급 유형(`PayoutType`, 2종): `SINGLE`(단일 정산), `TWO_PHASE`(분할 정산).

### 3-C. 상시 프로젝트 정산 스케줄 상태 (8종)

| 상태값 | 한글 라벨 |
|---|---|
| `GENERATING_DATA` | 정산 데이터 생성 중 |
| `DATA_GENERATED` | 정산 데이터 생성 완료 |
| `GENERATING_DOCUMENTS` | 문서 생성 중(정산명세서·세금계산서) |
| `FIXED` | 정산 확정됨 |
| `PROCESSING_PAYMENT` | 송금 처리 중 |
| `FULLY_PAID` | 전체 입금 완료 |
| `FAILED` | 정산 배치 실패 |
| `MANUAL_ADJUSTING` | 어드민 강제 수정 중 |

**전이 흐름**: `GENERATING_DATA → DATA_GENERATED`(배치 자동) → **`FIXED`(어드민이 API로 수동 확정)** → `PROCESSING_PAYMENT`(FIXED 상태에서만 진입 가능) → `FULLY_PAID`(이체 완료). 문서 생성(`GENERATING_DOCUMENTS`)은 `DATA_GENERATED`·`FIXED`·`FULLY_PAID` 상태에서 진입 가능하다. `MANUAL_ADJUSTING`은 `FULLY_PAID` 상태에서만 진입 가능하다(어드민 강제 수정).

- **재생성 불가(잠금) 상태**: `GENERATING_DATA`, `GENERATING_DOCUMENTS`, `FIXED`, `PROCESSING_PAYMENT`, `FULLY_PAID`, `MANUAL_ADJUSTING`. 결과적으로 정산 데이터를 다시 생성할 수 있는 상태는 사실상 `DATA_GENERATED`와 `FAILED` 뿐이다.
- **조회 가능 상태**: `DATA_GENERATED`, `GENERATING_DOCUMENTS`, `FIXED`, `PROCESSING_PAYMENT`, `FULLY_PAID`, `MANUAL_ADJUSTING`.
- **확정 이후 상태 그룹**: `FIXED`, `PROCESSING_PAYMENT`, `FULLY_PAID`.
- 문서 생성은 분기(Quarter) 단위 일괄 잠금도 지원한다.

### 3-D. 상시 정산 하위 상태·구분값

| Enum | 값(전체) | 의미 |
|---|---|---|
| `SettlementSummary.State` (3종) | `CREATED` / `PAID` / `FORCED_RECREATED` | 데이터 생성됨 / 입금 완료 / 정산금 이체 완료 후 어드민 강제 재생성 |
| `SettlementTransfer.RecipientType` (2종) | `TUMBLBUG` / `CREATOR` | 이체 수취인 구분 |
| `SettlementTransfer.State` (2종) | `CREATED` / `RESPONDED` | 이체 응답 전 / 응답 옴 |
| `SettlementDetailType` (2종) | `REWARD` / `EXTRA_BACKING` | 선물 구매 / 선물 구매 없는 순수 추가 후원금 |
| `TaxpayerType` (2종) | `INDIVIDUAL`("개인사업자") / `BUSINESS`("법인사업자") | 세금계산서 발행용 납세자 구분 |

- 상시 정산의 최종 정산 금액(`SettlementSummary`)은 소속된 모든 정산 명세(`SettlementDetail`) 건의 정산 금액을 합산한 값이다.
- `SettlementSummary`는 납세자 정보(사업자번호/주민등록번호)와 계좌·예금주 정보를 암호화하여 함께 보유한다.

## 4. 분할 정산 (Two-Phase Payout)

**조건부 수동 분할 정산**은 펀딩 특성상 모금액을 전부 받지 못하면 선물 제작이 어려울 수 있어, 정산을 완전히 보류하는 대신 **일부 금액을 먼저(1차) 지급**하고 나머지를 나중(2차)에 지급하는 제도다.

- 관리 대상 필드: 활성 여부, 1차 지급 완료 여부, 2차 지급 완료 여부, 1차 지급액, 2차 지급액, 1차 대상 후원금액, 총 수수료.
- **2차 정산 스케줄 타입**은 `AUTO` 또는 `MANUAL`(문자열 값) 두 가지다. `MANUAL`이면 운영자가 지정한 날짜에 2차 정산이 실행된다 — 이것이 "조건부 수동 분할 정산"의 실체다.
- 두 지급이 모두 완료된 경우에만 분할 정산 전체가 완료된 것으로 본다.
- 정산 대상 추출 시, 분할 정산 대상 프로젝트는 일반 정산 대상에서 제외되며 1차/2차는 각각 별도 로직으로 처리된다.

---

## 5. 세금계산서 / 정산명세서

### 5-A. 상시 프로젝트 정산

`GENERATING_DOCUMENTS` 상태에서 다음 문서를 생성한다:
- 세금계산서
- 정산명세서(창작자용 리포트)
- 판매대행 문서

문서 생성은 위 §3-C대로 `DATA_GENERATED`·`FIXED`·`FULLY_PAID` 상태에서만 진입 가능하다. 납세자 유형(§3-D `TaxpayerType`)에 따라 개인사업자/법인사업자 서식이 구분된다.

### 5-B. 펀딩/프리오더 정산

정산 실행 전 세금계산서 항목을 미리 생성(upsert)해두는 절차가 있으며, 프리오더의 텀블벅 수수료는 "결제 반영 금액 × 수수료율"로 산정된다.

---

## 6. 정산 트리거 (정산일 계산·실행)

### 6-A. 정산일 계산

| 유형 | 정산일 |
|---|---|
| 펀딩 | 결제 종료일 + 7영업일 |
| 프리오더(기본) | 전 선물 배송완료 후 "마지막 배송일 + 14일"(단, 마지막 환불 처리 기한과 비교해 더 늦은 날짜 적용) + 1영업일 |
| 분할정산 1차 | 별도 지정일(있으면) 또는 펀딩 잔금 정산일 |
| 분할정산 2차 | 별도 지정일(있으면) → `MANUAL`이면 운영자 지정일 → 아니면 프리오더 기본 정산일 |

- 정산 대상 판정은 "정산일 = 오늘"인지로 이루어진다.

### 6-B. 펀딩 정산 배치 오케스트레이션

정산일이 되면 배치가 대상 프로젝트별로 아래 순서를 실행한다.

1. 미결제 후원 정리
2. 세금계산서 항목 생성
3. 정산 검증(후불광고 차감 확정 여부 등 — 검증 실패 시 Slack 알림 후 해당 건은 스킵)
4. 정산 금액 계산(§2-A) — 계산 결과가 0 미만이면 정산 중단
5. **창작자 송금** — 실패 시 상태를 `SUCCEEDED_NOT_BALANCED`로 유지해 다음 배치 실행 시 재시도 가능(멱등)
6. **텀블벅 수익계좌 송금** — 이 단계가 실패해도 정산 자체는 성공 처리되며 별도 재송금 절차는 없음
7. 상태 전이(`SUCCEEDED_NOT_BALANCED → SUCCEEDED_BALANCED`)와 지급일시 기록
8. 검색 색인 갱신

- 텀블벅 예수금 계좌에서 수익 계좌로의 송금은 별도 기록으로 남으며, 성공 여부는 은행 응답 코드로 판정한다.

### 6-C. 상시 정산 실행 흐름

배치가 매월 정산 데이터를 생성(`GENERATING_DATA → DATA_GENERATED`)한 뒤에는 **자동으로 송금까지 진행되지 않는다.** 어드민이 API로 데이터를 확정(`FIXED`)해야만 송금 잠금(`PROCESSING_PAYMENT`)이 걸리고, 이체가 완료되면 `FULLY_PAID`로 전이한다. 즉 상시 정산은 "배치 자동 실행"인 펀딩 정산과 달리 **어드민 확정 게이트를 반드시 거치는 구조**다.
