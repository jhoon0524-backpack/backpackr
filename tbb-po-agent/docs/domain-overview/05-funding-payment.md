## 예약결제(빌링) 상태머신 — `ProjectWarrantyState`

후원 1건(`ProjectWarranty` 엔티티) 단위의 결제/보증 상태. DB 정수 value 0~11, 총 12개 값. 화면 노출 라벨은 상품 유형(기간 펀딩/프리오더/상시)과 결제 맥락에 따라 다르게 표기된다.

| value | 코드명 | title(기본) | 펀딩용 라벨 | 프리오더용 라벨 | 상시(store)용 라벨 | 결제 라벨 |
|---|---|---|---|---|---|---|
| 0 | `PLEDGED` | 결제 예약 | 후원 예약 | 예약 주문중 | (—) | 결제 예정 |
| 1 | `CANCELLED` | 밀어주기 취소 | 후원 취소 | 예약 주문 취소 | 결제 취소 | 결제 예약 취소 |
| 2 | `PAID` | 결제 완료 | 후원 성공 | 예약 주문 성공 | 결제 완료 | 결제 완료 |
| 3 | `UNPAID` | 결제 재시도 중 | 결제 재시도 중 | 결제 재시도 중 | 결제 재시도 중 | 결제 예정 |
| 4 | `DROPPED` | 결제 누락 | 결제 최종 실패 | 결제 최종 실패 | 결제 실패 | 결제 최종 실패 |
| 5 | `CHARGING` | 결제 대기 | 후원 예약 | 예약 주문중 | 결제 대기 | 결제 예정 |
| 6 | `PLEDGED_NOT_CHARGED` | 결제 예약 취소 | 후원 취소 | 예약 주문 취소 | (—) | 결제 예약 취소 |
| 7 | `REFUND_REQUESTED` | 환불 요청중 | 환불 요청중 | 환불 요청중 | 환불 요청중 | 결제 완료 |

| 9 | `REFUND_PROCESSING` | 환불중 | 환불 완료 | 환불 완료 | 환불 중 | 결제 취소 |
| 10 | `REFUNDED` | 환불 완료 | 환불 완료 | 환불 완료 | 환불 완료 | 결제 취소 |
| 11 | `INIT` | (빈값) | (빈값) | (빈값) | 결제 진행중 | 결제 진행중 |

**상태 버킷** (청구/집계 로직에서 사용하는 상태 그룹):

| 버킷 | 포함 상태 | 의미 |
|---|---|---|
| `CHARGEABLE_STATES` | UNPAID, CHARGING | 청구 대상 |
| `PENDING_STATES` | CHARGING, UNPAID | 결제 대기/재시도 |
| `PAYMENT_SUCCESS_STATES` | PAID, REFUND_REQUESTED, REFUND_REJECTED | 결제됨(환불 미포함) |
| `PAYMENT_RECEIVED_STATES` | PAYMENT_SUCCESS_STATES + REFUND_PROCESSING, REFUNDED | 결제 이력 있음(환불 포함) |
| `BACKING_SUCCESS_STATES` | PLEDGED, UNPAID, CHARGING, PAID, REFUND_REQUESTED, REFUND_REJECTED | 후원 성공으로 집계 |
| `BACKING_FAILED_STATES` | CANCELLED, DROPPED, PLEDGED_NOT_CHARGED, REFUND_PROCESSING, REFUNDED | 후원 실패로 집계 |
| `DIGITAL_ASSET_DOWNLOADABLE_STATES` | PAID, REFUND_REJECTED | 디지털 에셋 다운로드 허용 |

> ⚠️ REFUND_REJECTED·REFUND_REQUESTED는 `PAYMENT_SUCCESS_STATES`에 포함된다. 즉 환불 거절/요청 중이어도 "결제됨"으로 집계된다 — 정산·집계 지표 설계 시 유의.

### 전이 시퀀스 (기간 펀딩=예약결제, All-or-Nothing)

1. **후원 시** → `PLEDGED`(0): 후원번호 생성 + 결제정보(빌링키/카드) 저장, 실청구 없음(예약). 진행기간 중 결제수단 변경 가능.
2. **프로젝트 마감 & 성공 판정** → `PLEDGED` → `CHARGING`(5): 마감 처리 배치가 **성공한 프로젝트의 후원만** CHARGING으로 전이한다. **실패(목표 미달) 프로젝트는 여기서 제외되어 청구 자체가 시작되지 않는다** — All-or-Nothing 불변식의 코드 근거.
3. **청구 배치** → CHARGING/UNPAID 대상 결제 시도 → 성공 시 `PAID`(2), 실패 시 `UNPAID`(3).
4. **재시도** → UNPAID/CHARGING(청구 대상)은 자연일 7일간 매일 재청구.
5. **7일째까지 실패** → pending(CHARGING, UNPAID) 후원을 일괄 `DROPPED`(4)로 전이 + 빌링키 만료 처리.

> 명시적 전이 Enum(`ProjectWarrantyStateEvent`)에는 `MARK_AS_CANCELLED`(PLEDGED→CANCELLED) 1건만 선언돼 있고, 대부분의 전이는 서비스/배치가 직접 상태를 갱신하는 절차적 처리다(선언적 상태머신 미구현).

## All-or-Nothing 청구 배치

- **청구 시작**: 마감일 도달 프로젝트 중 **성공** 건의 후원만 PLEDGED→CHARGING 전이. 실패 건은 전이 없음(=미청구).
- **후원 결제(청구) 배치**: 단일 Job, 3 Step **순차 실행** — 네이버페이 → 간편결제(아임포트) → 카드. 각 Step은 완료된 상태에서도 재시작 가능하도록 설정돼 있다.
  - ⚠️ **계좌(BANK_ACCOUNT) 청구 Step이 없다** — Java 배치는 네이버페이·간편결제(아임포트)·카드 3종만 처리한다(아래 「노션 ↔ 코드 불일치」 참조).
  - 각 Step은 커서 페이징(최대 20건)으로 CHARGING/UNPAID + 해당 결제수단 + **상시(STORE) 프로젝트 제외** 대상을 조회한다. 비동기 병렬 처리 로직은 현재 비활성화되어 순차 실행된다.
  - 카드 실청구는 나이스페이 빌링키를 사용한다.
- **청구 멱등성/정합성 가드**:
  - 프로젝트가 취소됐거나 결제기한이 지났으면 skip
  - 청구 대상 상태(CHARGING/UNPAID)가 아니면 skip → PAID/DROPPED 후원의 재청구 차단
  - 이미 결제 처리 중인 건(직전 시도 결과 존재)이면 skip — **중복청구 방지 핵심 가드**
  - 조회 시점과 배치 진입 시점 사이에 결제수단이 변경된 건은 "변경된 결제내역"으로 간주해 무시
  - 빌링키가 없는 건은 skip, 농협 문화누리카드는 카테고리 제한 적용
  - PG 응답 파싱 오류 시 상태를 CHARGING으로 복원 후 예외를 던져 다음 배치에서 재시도되도록 보장
- **결제 누락 정리 배치**: 대상은 "성공·정산전(SUCCEEDED_NOT_BALANCED)" 프로젝트 중 마감일이 오늘 기준 8일 전인 것. 대상 프로젝트의 pending(CHARGING, UNPAID) 후원을 일괄 DROPPED 처리하고, 네이버페이/아임포트 빌링키를 만료 처리한다.

### 배치 실행 시각 (노션 정책 vs 코드)

- **노션 정책**: 종료일 다음날부터 **자연일 7일** 결제 시도, 매일 **오후 2~3시**에 결제수단별 배치 시작 — **네이버페이 14:15 / 계좌 14:30 / 카드 14:45**. 결제수단 변경 시 **1분 후** 변경된 수단으로 결제 시도. 성공하면 더 이상 시도하지 않고 후원 완료(선물 수령 가능), 실패는 7일 재시도 후 "결제 누락"(선물 불가) 처리.
- **코드 기준**: be-api Java 배치에는 cron/스케줄 정의가 없다(Job 정의만 존재). 실행 시각은 인프라 스케줄러(Kubernetes CronJob 등) 소관이며, 노션이 명시한 시각은 코드에서 확인되지 않는다. Job 내 Step 순서(네이버페이→아임포트→카드)는 노션이 명시한 순서와 부분 일치하나 **계좌가 누락**돼 있다.

| 효성(계좌이체) | 결제시도 50원 + 결제성공 650원 = 성공 시 700원 | O | X |
| 네이버페이 | 2.4% | O | X |
| 가상계좌 | 결제건별 기본 300원 + 에스크로 200원 (금액 무관) | X | O |
| 토스페이먼츠 | 2.2% | X | O |
| 카카오페이 | 2.25% | X | X |

> **PO 확인 (2026-07-09)**: 나이스페이(카드)는 **아임포트를 통해 계약하지 않으며**, 계약 수수료(PG 원가)는 현재 **2.22%** — NicePay 가맹점 관리자 콘솔에서 조회 가능. 노션 원문에는 "아임포트 통해 계약 시 2.2%, 아니면 2.3%"로 기재되어 있으나 위 표는 PO 확인값으로 갱신했다.

### 코드 실측값 (`WithdrawResult.commission` — 정산 차감 기준)

결제 성공 시 정산에서 창작자 몫 차감에 쓰이는 PG수수료 기록값. 율 자체는 대부분 config 주입값이며, NicePay 카드만 코드에 하드코딩돼 있다.

| 결제수단 | 수수료율 | 값 출처 | 계산식·반올림 |
|---|---|---|---|
| 카드(NicePay) | payoutVersion 4/5/6 → **2.4%**, 그 외 → **2.8%** | 코드 하드코딩(환경 무관) | `Math.round(금액 × 율)` → 원단위 반올림(HALF_UP) |
| 네이버페이 v2 | card·bank·npoint 모두 **2.4%** | config 주입값 | `Math.round(주결제금액 × 율) + Math.round(포인트결제금액 × 포인트율)` |
| 네이버페이 v1(잔존) | card **2.9%** / bank **1.5%** / npoint **2.9%** | config 주입값 | 상동. v1/v2는 버전 플래그로 분기 |
| 간편결제(아임포트 경유: 카카오페이·토스페이 등) | 결제수단이 카드면 **2.5%**, 그 외(카카오페이 등 포인트성 결제)도 **2.5%** | config 주입값(dev·prod 동일) | `Math.round(금액 × 율)` |

- **반올림 모드 통일**: 세 경로 모두 `Math.round(double)` = 최근접 정수(원) 반올림, 소수 .5는 올림(양수 기준 HALF_UP). `BigDecimal.setScale`이 아니다.
- 결제 실패 시 commission=0, chargedAmount=0으로 기록된다.

> **결제수수료 SSOT 이원화 확정 (PO 확인, 2026-07-09)**: 결제수수료는 목적이 다른 두 값으로 나뉜다 — ① **계약 원가 SSOT**: NicePay 가맹점 관리자 콘솔 기준 현재 2.22%(노션 표 2.2%는 소폭 갱신 지연). ② **정산 차감값 SSOT**: 코드의 `WithdrawResult.commission`(payoutVersion 분기 2.4%/2.8%) — 실제 창작자 정산에서 차감되는 값. 두 값은 애초에 서로 다른 목적을 가진 별개 값이며, 노션표를 코드에 맞출 필요도 코드를 노션에 맞출 필요도 없다. 정산 동작 자체를 좌우하는 것은 코드값이므로, 아래 「노션 ↔ 코드 불일치」는 코드 기준으로 판정한다.

## 기간 펀딩(예약결제) vs 상시 프로젝트(즉시결제)

| 구분 | 기간 펀딩(예약결제) | 상시 프로젝트(즉시결제) |
|---|---|---|
| 프로젝트 판별 | 일반 | 상시(store) 타입 & 상태가 "진행중/목표도달" |
| 결제 시점 | 마감 후 배치 청구 | 후원 즉시 |
| 상태 전이 | PLEDGED→CHARGING→PAID/UNPAID→DROPPED | INIT(11)→(확정)→PAID(2) 직결 |
| 배치 청구 대상 | 포함 | **제외**(청구 배치가 상시 프로젝트를 걸러낸다) |
| 허용 결제수단 | 카드·계좌·네이버페이·간편결제 | **카드 또는 간편결제(아임포트)만** |
| 부가 처리 | — | 결제 즉시 디지털 에셋 배송, 선물 상태를 배송완료로 갱신, 결제일시·배송일시 기록 |
| 공통 선행 조건 | 연락처 점유인증 필수 | 동일 |
| 수량 제한 | — | 1회 구매 수량이 선물별 구매 한도를 초과하면 거부 |

## 프로젝트 상태 (`ProjectState`, 결제 관련)

전체 14개 값:
`DRAFT`(작성 중) · `SUBMITTED`(승인요청 됨) · `VERIFIED`(승인 됨) · `REJECTED`(보완 요청 됨) · `FINAL_REJECTED`(반려 됨) · `CANCELLED`(취소 됨) · `FAILED`(실패) · `ONGOING_NOT_REACHED`(진행 중) · `ONGOING_REACHED`(진행 중/목표금액 도달) · `SUCCEEDED_NOT_BALANCED`(성공) · `SUCCEEDED_BALANCED`(성공/정산완료) · `PRELAUNCHED`(공개예정 중) · `PAUSED`(일시 중지, 상시 전용) · `ENDED`(판매 종료, 상시 전용)

- **All-or-Nothing 판정 핵심**: `SUCCEEDED_NOT_BALANCED`(목표달성·정산 전)만 청구 대상이며, `FAILED`는 청구 대상에서 제외된다(=미청구).
- `SUCCEEDED_STATES` 버킷 = {`SUCCEEDED_NOT_BALANCED`, `SUCCEEDED_BALANCED`}.

## 노션 ↔ 코드 불일치

**전제**: 노션 「결제 수수료」 표는 PG사 계약 수수료(원가) 관점이고, 코드의 `WithdrawResult.commission`은 정산에서 창작자 몫 차감에 실제 쓰이는 기록값이다. 목적이 다를 수 있으나 실제 정산 동작을 좌우하는 것은 코드값이므로, 아래는 코드 실동작을 기준으로 판정한다.

1. **카드(NicePay) 수수료율** — 노션 문서는 2.2%(아임포트 계약 시)/2.3%(그 외)로 기재(코드 기준 payoutVersion 4/5/6이면 2.4%, 그 외 2.8%, 코드 하드코딩). 값뿐 아니라 분기 기준 자체가 다르다 — 노션은 "아임포트 계약 여부", 코드는 "payoutVersion(창작자 정산버전)" 기준. **PO 확인(2026-07-09) 결과 이 "불일치"는 계약 원가(가맹점 관리자 기준 2.22%)와 정산 차감값(코드 2.4%/2.8%)이 서로 목적이 다른 별개 값이기 때문으로 확정되었다 — 둘을 일치시켜야 할 오류가 아니다. 또한 나이스페이는 아임포트를 통해 계약하지 않음이 함께 확인되어, 노션의 "아임포트 계약 시" 분기는 현행 사실이 아니다.** payoutVersion 분기 자체의 사업적 근거(어떤 창작자가 어느 버전인지)는 여전히 확인 필요.
2. **카카오페이 수수료율** — 노션 문서는 2.25%로 기재(코드 기준 2.5% — 카카오페이는 간편결제(아임포트) 경유로 처리되어 포인트성 결제 수수료율이 적용됨). 0.25%p 차이.
3. **계좌(효성) 결제 청구·수수료** — 노션 문서는 정액 "결제시도 50원 + 결제성공 650원 = 700원"과 매일 14:30 배치 청구로 기재(코드 기준 be-api Java에는 계좌 청구 배치·수수료 계산 로직이 없음 — 청구 배치는 네이버페이·간편결제·카드 3종만 처리). 계좌 결제 청구는 Ruby 잔존 코드 또는 별도 경로로 처리되는 것으로 추정되며, be-api(Java) 범위에서는 확정할 수 없다.
4. **네이버페이 수수료율** — 노션 문서는 2.4%로 기재(코드 기준 v2는 2.4%로 일치). 다만 코드에 v1 로직이 잔존해 있어, v1 적용 후원 건은 card 2.9%/bank 1.5%/npoint 2.9%로 노션표와 다른 율이 적용된다.
5. **토스페이먼츠 수수료율** — 노션 문서는 2.2%(광고센터 전용)로 기재. 서비스(후원) 결제의 토스페이는 간편결제(아임포트) 통합 경로로 처리되어 포인트성 결제 수수료율(2.5%)이 적용되며, 노션의 2.2%는 광고센터 전용 결제수단에 대한 값이라 서비스 후원 결제 수수료와 직접 비교 대상이 아니다.

## `[확인 필요]`

> ~~**결제수수료 SSOT 정의**~~ — **해소됨 (PO 확인, 2026-07-09)**: NicePay 가맹점 관리자 콘솔 기준 계약 원가 2.22% 확인 완료. 계약 원가 SSOT(가맹점 관리자)와 정산 차감값 SSOT(코드)로 이원화된 것이 확정된 정상 설계임을 확인했다. 상세는 위 「결제 수수료」·「노션 ↔ 코드 불일치」 1번 참조.

1. **NicePay payoutVersion 4/5/6 → 2.4% / 그 외 2.8% 분기의 사업적 근거** — payoutVersion이 무엇을 의미하고 어떤 창작자가 어느 버전에 해당하는지는 정산팀 확인이 필요하다.
2. **`KAKAO_PAY`(`PaymentType` value 4) 실사용 여부** — 실결제는 `IAMPORT`(3) 경유로 처리되는데 별도 코드값 4가 존재한다. 활성 상태인지 레거시 잔존인지는 결제팀 확인이 필요하다.
3. **계좌(효성) 결제 청구의 실제 처리 위치** — be-api(Java)에는 청구 로직이 없다는 점은 확정됐으나, Ruby 레거시에 남아있는지 별도 경로가 있는지는 엔지니어링 이관 로드맵 확인이 필요하다.
