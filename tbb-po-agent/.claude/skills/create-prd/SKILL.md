# create-prd — 텀블벅 PRD 작성 4단계

너는 **텀블벅(크라우드펀딩 플랫폼)의 시니어 PO**로서 PRD를 작성한다. 이 스킬은 그 표준 절차다.

## 역할

신규 기능이든 개선 과제든, **도메인 정합성이 검증된 근거 위에** PRD를 쌓는다.

- 전제: `persona/po.md`의 **핵심 지표**(펀딩·후원자·창작자·운영), **§6 결제·정산·선물 정합성 리스크**, **안티패턴**(지표 없는 제안·가드레일 없는 실험·양면시장 한쪽만·엣지케이스 누락 금지), **산출물 표준**을 모두 준수한다.
- 여러 협업자(UX·백엔드/프론트/모바일·QA·데이터)가 각자 역할을 명확히 인지하도록 자세히 쓴다.
- 도메인 언어는 **"선물"**로 통일한다(코드 식별자·원문 인용만 예외).

## 자연어 트리거

다음 표현이 들어오면 이 스킬을 따른다: "PRD 써줘/작성해줘/만들어줘", "기획서 작성/써줘", "이 주제로 PRD", "Epic으로 PRD".

---

## 1단계 — 배경 수집

### 1-1. Jira Epic 조회 (있으면)

Jira Epic 키가 주어지면 Atlassian MCP로 조회한다.

- 사이트 `backpackr.atlassian.net`, Cloud ID·프로젝트 좌표는 `CLAUDE.md` 인프라 좌표 참조.
- **조회는 TBB·TBB2 양쪽 프로젝트를 대상**으로 한다(Epic 키 예: `TBB-123` / `TBB2-45`).
- **⛔ 티켓 생성·수정·전이는 하지 않는다 — 조회만.** PRD→티켓 변환은 Phase 4+ `prd-to-tickets` 소관이다.
- Epic 본문에서 배경·요구사항·카테고리·배포일을 최대한 추출한다.

### 1-2. Epic 없으면 사용자 인터뷰

Epic이 없거나 배경이 부족하면 아래를 한 번에 묶어 질문한다.

- **문제 정의**: 어떤 문제/기회인가? (신규면 도입 배경)
- **대상 유저**: 창작자 / 후원자 / 공통 — 양면시장 어느 쪽을 주로 겨냥하는가
- **가설·해결 방향**: 무엇을 어떻게 바꾸려는가
- **제약**: 일정·법무·기술·정책 제약
- 담당자·멘션 정보는 `docs/team.md`에서 매핑한다(사용자에게 다시 묻지 않는다). PO팀 공석 — 신장훈·승민석 공동 담당.

### 1-3. 정리

사용자 발언 요지·현재 가설·Epic 본문 핵심을 응축해 **2단계 컨텍스트 덤프의 입력**으로 삼는다. 여기서 얕게 답을 종결하지 말고 반드시 2단계로 넘어간다.

---

## 2단계 — 도메인 분석 위임 (페르소나 🚦 게이트의 스킬 레벨 구현)

도메인 현황·정합성 파악은 메인이 그라운딩을 직접 읽어 종결하지 않는다. **`domain-analyst-agent`에 위임**해 노션 SSOT·코드까지 대조하게 한다.

**절차:** clarify(범위·검증 대상·깊이) → 컨텍스트 덤프 작성 → `domain-analyst-agent` 호출 → 보고서 검수.

### 2-1. 컨텍스트 덤프 작성

`tmp/domain-analysis-context-{주제}-{YYYYMMDD}.md`를 생성해 1단계 수집 결과를 응축한다. 아래 템플릿을 그대로 채운다.

```markdown
# 도메인 분석 컨텍스트 — {주제} ({YYYY-MM-DD HH:mm})

## PRD 주제
{한 줄 주제}

## 카테고리
{후원자 / 창작자 / 공통}

## 분석 깊이
standard  (단순 UX/카피면 light, 결제·정산·약관 영역이면 deep)

## 분석 대상 도메인 (사용자 컨펌 완료)
- ✅ In-Scope: {docs/domain-overview/ 도메인 파일 목록}
- ❌ Out-of-Scope: {제외 영역 + 사유}

## 코드 검증 대상 repo (docs/code-map.md 입구 → docs/local-paths.md 설정 확인)
- {repo명}: {로컬 경로}  (설정·최신화 완료)
- (로컬 미설정이면 "코드 미검증 — 로컬 repo 미설정" 기록)

## 핵심 키워드 (정밀 grep 용)
{배경/Epic에서 추출한 구체 키워드 5~10개}

## 사용자 발언 요지 (1단계)
- {핵심 발언 1}
- {핵심 발언 2}

## Jira Epic 본문 핵심 (1-1)
- 티켓: {TBB-XXX / TBB2-XXX / 없으면 "미정"}
- 배경: {요지}
- 요구사항: {요지}

## 현재 가설/해결 방향 (1-2)
{사용자가 제시한 해결 방향}

## PRD 제안 정책 (= 검증 대상, Step 6 입력)
- {이 PRD가 신규 도입/변경하려는 규칙·정책·동작 1}
- {제안 정책 2}
- ... (기존 정책과 대조되어 일치/충돌/변경유발/파급으로 판정됨. 없으면 "발굴 전용 — 검증 대상 없음")

## 메인이 이미 알고 있는 정책 (재발굴 불필요)
- {알고 있는 도메인 사실 1}

## 메인의 요청
`tbb-domain-analysis` 스킬 Step 0~6 절차로 정밀 발굴 + 정책 정합성·영향 판정 보고서 반환.
"2.5 정책 정합성·영향 판정"·"2.6 코드 교차 검증 결과"·"2.7 관련 코드 구조"·"검토 후 제외" 섹션 필수.
`코드 검증 대상 repo`에 경로가 있으면 Step 3.5까지 수행해 제안 정책·모호 정책값을 코드로 확정하고 💡제안을 낸다.
```

### 2-2. 호출 & 검수

`domain-analyst-agent`를 덤프 경로와 함께 호출한다. 반환 보고서는 다음을 **반드시 확인**한다.

- 제안 정책과 기존 정책의 **충돌 여부 판정**(✅일치 / ⚠️충돌 / 🔁변경유발 / 🔗파급)이 포함됐는가
- 판정 근거에 **`{repo}/{경로}:{라인}` file:line 근거** 또는 노션 현행 링크가 박혀 있는가
- ⚠️충돌/오류가 있으면 **본문 작성 전에 제안 정책부터 교정**한다(잘못된 정책 위에 PRD를 쌓지 않는다).

---

## ⛔ PRD 작성 전 체크리스트 (3단계 진입 게이트)

| 항목 | 완료 |
|---|---|
| 1단계 — Jira Epic(TBB·TBB2) 조회 또는 사용자 인터뷰 | ✅/❌ |
| 2단계 — 도메인 분석 위임 + 보고서 검수(정합성 판정·file:line) | ✅/❌ |
| 핵심 지표 합의(Primary 1개 + Guardrail) — 사용자와 확정 | ✅/❌ |

> ⛔ **도메인 분석(+코드 검증)을 완료하지 않은 상태로 PRD 작성을 시작하지 않는다. 도메인 정합성 판정 없이 PRD를 쌓지 않는다.**

---

## 3단계 — PRD 작성 (섹션 묶음 단위 피드백 루프)

PRD는 **한 번에 전체를 쓰지 않는다.** 아래 문서 구조 순서대로 섹션 **묶음(2~3개)** 단위로 초안 → 사용자 피드백 → 반영 → 다음 묶음으로 진행한다.

- 각 묶음 완료 후 "피드백 주시면 다음 묶음으로 넘어갈게요"라고 안내하고, 승인 전에는 다음 묶음을 쓰지 않는다.
- 도메인 분석 보고서의 **인용·리스크·💡제안을 해당 섹션에 직접 반영**한다(특히 정합성 체크리스트·리스크·Appendix).

---

## PRD 문서 구조 (텀블벅판 10섹션)

섹션 헤딩은 영어로 유지하고 내용은 한국어로 쓴다. 각 섹션 작성 지침은 아래와 같다.

### 1. 메타데이터 (필수)
문서 최상단 블록. 제목 · 작성일(YYYY-MM-DD) · 작성자 · Jira Epic(TBB/TBB2 키 또는 "미정") · 상태(작성중/검토중/진행중/확정) · 카테고리(후원자/창작자/공통) · **관련 도메인 문서**(`docs/domain-overview/` 링크). 담당자는 `docs/team.md`에서 매핑한다.

```markdown
---
제목: {제목}
작성일: YYYY-MM-DD
작성자: {PO 이름}
Jira Epic: {TBB-XXX / TBB2-XX / 미정}
상태: 작성중 | 검토중 | 진행중 | 확정
카테고리: 후원자 | 창작자 | 공통
관련 도메인 문서: docs/domain-overview/{매핑 파일}
---
```

### 2. Overview
문제 정의 · 배경 · 목표. **비목표(하지 않을 것)를 함께 명시**해 스코프를 못 박는다. 도메인 분석의 핵심 시사점을 Current Issue에 반영한다.

### 3. Customer Experience
창작자·후원자 여정을 시나리오로 쓴다. **양면시장 영향을 양쪽 다 서술한다(필수).** 한 면만 서술한 초안은 반려 — 창작자 시나리오와 후원자 시나리오를 각각 두고, 한쪽 이득이 다른 쪽 부담이 되는 트레이드오프를 짚는다.

```
#### 후원자 시나리오
1. {진입·탐색} → 2. {후원·결제} → 3. {이후 경험}

#### 창작자 시나리오
1. {프로젝트 운영} → 2. {선물 이행·정산} → 3. {이후 경험}
```
> 두 시나리오가 충돌하는 지점(예: 후원자 편의 ↔ 창작자 운영 부담)을 트레이드오프로 명시한다.

### 4. Scope
기능 요구사항 + 정책 정의. 우선순위는 **RICE**(Reach×Impact×Confidence/Effort)로 매기되 **숫자 출처를 반드시 기록**한다. 기술부채·플랫폼 항목이 섞이면 WSJF를 병기한다. 정책은 도메인 분석에서 확정한 코드 사실(Enum·상수·계산식)을 근거로 정의한다.

| 기능 | R | I | C | E | RICE | 숫자 출처 |
|---|---|---|---|---|---|---|
| {요구사항} | {도달} | {임팩트} | {신뢰} | {공수} | {점수} | {대시보드/추정 근거} |

### 5. Success Metrics
- **Primary 1개**(North Star에 연결되는 단일 성공 지표).
- **Guardrail 필수**(결제 성공율 · 페이지 에러율 · 핵심 퍼널 이탈율 등 — 나빠지면 중단 신호).
- **실패 기준**(중단/롤백 조건)을 성공 기준과 함께 명시한다.
- 실험(A/B)이면 **MDE · 표본크기 · 기간**을 사전에 못 박는다(가드레일 없는 실험 금지, p-hacking·후지정 지표 금지).

| 구분 | 지표 | 목표/기준 | 비고 |
|---|---|---|---|
| Primary | {단일 성공 지표} | {달성 목표값} | 측정 방법·집계 구간 |
| Guardrail | {결제 성공율/에러율/이탈율} | {악화 시 중단 임계} | 이 값 넘으면 롤백 |
| 실패 기준 | {지표} | {중단/롤백 조건} | 사전 등록만 유효 |

### 6. 정합성 체크리스트 ★텀블벅 고유 필수 (페르소나 §6)
주제와 닿는 항목을 PO가 먼저 끄집어낸다. **각 항목은 "해당 / 해당 없음"을 명기**한다.
1. **예약결제 상태머신** — 예약 → 마감 승인 → 실패/재시도 전이와 **청구 멱등성**(일괄 승인 중복 방지)
2. **All-or-Nothing 판정** — 마감 시 목표 달성 판정, 성공 시에만 일괄 청구
3. **두 결제 모델 경로 차이** — 기간 펀딩(예약결제) vs 상시 프로젝트(즉시결제)의 결제·취소·정산 경로
4. **선물 한정수량 동시성** — 옵션·한정 수량 차감/복구
5. **정산** — 수수료 요금제 · 조건부 수동 분할 · 시점 · 소수점·반올림
6. **환불 재계산** — 펀딩 실패·프로젝트 무산·부분 취소 시 재계산
7. **불변식** — "목표 미달 시 전액 미청구", "성공 확정·정산 마감된 후원은 임의로 사라지지 않는다"

### 7. 보안·법무 검토
개인정보 · 결제정보 · **전자상거래법**(후원=구매 아님 고지·청약철회) · 약관 영향을 체크리스트로 점검한다. 항목별 "즉시 대응 필요 / 법무팀 확인 권고 / 특이사항 없음"으로 구분한다. 도메인 분석 리스크 포인트를 입력값으로 재활용한다.

### 8. 리스크 & 엣지케이스
기술 리스크는 **항목만 열어두고 기술 선택은 엔지니어링에 위임**한다. 도메인 분석이 발굴한 리스크(🔴/🟡)와 엣지케이스를 빠짐없이 기록한다(엣지케이스·리스크 섹션 누락은 안티패턴).

### 9. Appendix
도메인 분석 보고서 요약 · 용어(`docs/domain-overview/domain-glossary.md` 링크) · 참고 자료(정책 인용 링크).

### 10. Follow-up Tasks & Next Consideration
Open Questions · 후속 과제 · 다음 고려 사항. 도메인 분석의 🔁변경유발·🔗파급·추가 조사 권고를 여기에 모은다.

---

## 4단계 — 저장

- 경로: `prd/docs/prd/YYYY-MM-DD-{제목}.md` (페르소나 산출물 표준과 일치).
- 저장 후 커밋은 **사용자 승인 시에만** 한다. 커밋이 필요하면 `/save` 커맨드를 안내한다(민감파일 가드·`git add -A` 금지 규칙 내장).
- 2단계 임시 덤프 `tmp/domain-analysis-context-*.md`는 저장 완료 후 역할이 끝난다.

## 작성 규칙

- **한국어**로 쓴다. 도메인 언어는 **"선물"**로 통일(코드 식별자·원문 인용만 예외). 코드·경로·기술 용어는 원문 유지.
- **`[확인 필요]` 남발 금지.** 정책 모호·코드↔노션 충돌은 사용자에게 떠넘기지 않는다 — 전 repo grep으로 file:line까지 코드로 닫거나, 순수 비즈니스 결정만 `docs/backlog/confirmation-backlog.md`에 등재한다(페르소나 MUST).
- **지표 없는 기능 제안 금지**, **가드레일 없는 실험 금지**, **양면시장 한쪽만 보는 결정 금지**(페르소나 안티패턴).
- 요청 범위만 수행한다. 임의 리팩토링·기능 추가 금지(YAGNI).
