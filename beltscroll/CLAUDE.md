# 조선 퇴마전 (작업명 Belt Brawl) — 작업 규칙

이 파일은 매 작업 시작 시 반드시 읽고 따른다. `docs/progress.md`가 있으면 함께 읽고, 거기 적힌 현재 단계부터 이어간다.

## 1. 프로젝트 한 줄 정의
브라우저에서 도는 2D 벨트스크롤 액션 게임 "조선 퇴마전" (작업명 Belt Brawl). 1인 개발(오너는 비개발자), 클로드코드가 구현을 맡는다.
조선 마을의 밤, 벽사청 검객 윤무겸이 귀물(원귀·도깨비)과 싸운다. 웨이브 3개, 3연타(벽사검), 점프, 잡아 던지기, HUD, 터치 조작 (2026-10-27 오너 지시로 세계관 전환, 상세 `docs/joseon-p0.md`).
- 공식 아트 기준: `assets/reference/` 설정화 (경량 WebP 7장 + `png-originals/` PNG 원본, 구분은 그 폴더 README).
- 게임 속 캐릭터는 `art.js` 가 코드로 그린 **임시 전투 스프라이트**다. 정식 스프라이트는 `data/sprites.js` + `docs/sprite-spec.md` 구조로 교체하며, 교체해도 판정·타격감은 그대로다.
- 데이터 이름은 예전 그대로다: 적 `thug`(그림 `wongwi` 원귀)·`brute`(그림 `dokkaebi` 도깨비), 주인공 그림 `mugyeom`.
- 주인공은 직업(`data/classes.js`)마다 사거리·판정 방식이 다르다: 조선 = 벽사검객(칼, 몸 접촉 판정), 밤거리 = 격투가(주먹, 원래 판정). 앞으로 파귀무인·벽력포수·봉령술사 등도 여기에 한 줄씩 (아직 만들지 않음).
- 원래의 현대 밤거리 격투(격투가·주먹 판정)는 코드에 남아 있고 주소 끝에 `?theme=street` 를 붙이면 볼 수 있다 (적 그림은 data 의 art). 조선 전환 전 버전은 브랜치 `ccr-05037f70-jcsww6`.
지금 목표는 기능 추가가 아니라 "손맛"을 끌어올리는 것이다.

핵심 가설: 손맛 = 입력 응답(선입력·즉시 발동) × 타이밍(준비·판정·경직 프레임) × 피드백(히트스톱·흔들림·넉백·플래시·소리).
애니메이션 프레임을 늘리는 대신 이 세 축을 조정해 손맛을 낸다. 피드백만 올려서는 안 된다. 리듬(입력 응답·타이밍)이 먼저다.

## 2. 데이터와 코드의 경계 (느낌이 확정된 뒤에 옮긴다)
- 타격감 수치는 처음부터 `FEEL` 한 곳에 모은다.
- 그 외 수치(적 능력치, 웨이브, 판정 거리 등)의 파일 분리는 오너가 손맛을 확정한 뒤에 한다. 느낌이 안 정해진 수치를 먼저 옮기지 않는다.
- 새로 짜는 코드는 숫자를 여기저기 흩어 쓰지 않는다. 한 번에 전부 갈아엎지 않는다.

## 3. 바리에이션 규칙 (스타일 일관성)
- 새 적·새 이펙트는 0부터 만들지 않는다. 기존 것(원귀 wongwi·도깨비 dokkaebi, 원래 thug·brute, 기존 이펙트)을 복제해서 시작한다.
- 모양·색·비율은 `assets/reference/` 설정화를 기준으로 맞춘다 (윤무겸은 03 설정화, 색은 03 의 주요 색상 견본).
- 복제본에서 바꿔도 되는 값: 팔레트, 크기 비율, 속도, 개수, 틴트, 수명, 데미지·체력, 타격감 수치.
- 바꾸면 안 되는 것: art.js의 그림 구조, 픽셀 크기(ART.S), 이펙트의 구성 방식. 바꿔야 하면 이유와 함께 먼저 보고하고 오너 확인을 받는다. (2026-10-27 조선 전환 때 추가한 것: 도포·소복 자락 단계, 칼 든 자세, 잡기용 맨손 별칭 포즈, 정식 스프라이트 교체 함수. 2026-10-28: 그림 전체를 가로로 옮기는 값(임시 3타 찌르기 그림 한정 — 오너 결정: 임시 그림은 더 고치지 않고 P1 정식 3타 준비·찌르기·회수 3칸으로 해결), 판정용 모양 기록(`hitShapes`: 가드 주먹·칼날 칸). 원래 3종 그림은 픽셀 단위로 그대로)
- 그림과 판정은 같은 자리다 (2026-10-27 오너 결정, 벽사검 사거리 확장): 윤무겸 1·2·3타(칼)는 칼끝 = 판정 끝 = 몸 중심 앞 57px (art.js `SWORD_TIP` 18칸, index.html `ATTACKS` reach 57), 명중은 "칼끝이 적의 몸 앞끝(`data/enemies.js` 의 `hurtHalfWidth`, 걷는 실루엣 기준·뻗은 주먹 제외 27px)에 닿으면", 또는 "칼날이 서 있기·걷기 그림의 가드 주먹(몸 앞끝 밖으로 나온 주먹)에 가로·높이 모두 실제로 겹치면" (2026-10-28 오너 결정, 다른 자세의 주먹·몸 폭·잡기·밀기는 그대로, `tests/fists.js`). 3타 찌르기는 칼날 48px(그림 전체를 5칸 뒤로 물려 40칸 프레임 안에서), 1·2타는 대각선 약 54px. 몸 앞끝 값도 그림에서 재서 정한다 (`w` 는 그림자·밀기용이라 따로). 그림과 판정 차이는 `tests/reach.js` 로 3px 이내. 칼 그림을 바꾸면 판정도 같이 측정해 맞추고, 판정을 바꾸면 그림도 같이 바꾼다. 적 주먹 끝은 적 사거리(52px) 이하.
- 캐릭터 그림은 40칸 프레임(화면 120px) 안에 들어가야 한다. 더 크게 하려면 프레임을 키우는 구조 변경이라 먼저 보고한다.
- art.js에 이미 있는 포즈(예: windup)를 먼저 찾아 쓰고, 새 포즈는 꼭 필요할 때만 만든다.

## 4. 손맛 설계 규칙과 검수
- 사거리 여유 규칙: 적이 플레이어 앞에서 자연스럽게 멈추는 거리와 약공격(1타 기준) 사거리 사이에 8px 이상 여유를 둔다. 제자리 연타가 헛스윙하면 버그다. 단, 공격을 예고 중인 적(예고 시작 거리 `attackStartOf(e)`)은 예외다 — 한 걸음 들어가 치거나 물러나 피하는 상황이다 (2026-10-27 오너 결정).
- 예고는 사거리 밖에서 (1타 기준): 적은 주인공 공격(1타)이 그 적에 닿기 시작하는 거리보다 8px 밖에서 공격 준비를 시작한다 (`attackStartOf(e)` = 1타 사거리 + (칼 판정이면 몸 앞끝) + 8 → 벽사검객 상대 92, 격투가 상대 56). 3타 찌르기는 서 있는 도깨비의 가드 주먹까지 적 중심 92px 에 닿아 이 여유가 0이지만, 예고·달려들기 그림엔 주먹 판정이 없어 예고를 끊지 않는다 (2026-10-28 오너 결정 (가): 예고 거리 92 유지, `tests/fists-group.js`). 주인공 사거리를 바꾸면 이 값과 돌진 거리(예고 시작 거리 − 32px)가 같이 바뀌어, 물러나 피할 시간과 적 적중률이 그대로인지 `tests/dodge.js`·`tests/dominance.js` 로 전후 비교한다. 벽사검객 상대 돌진은 9프레임, 고르게 점점 빨라지게(프레임당 3.3px → 10px, 2026-10-28 오너 결정), 뛰는 그림(rush).
- 넉백은 비율이 아니라 역할로 정한다: 약공격은 적이 다음 타 사거리 안에 남는 거리, 피니시(3타·점프 공격·사망 타격)는 확실히 날아가는 거리.
- 흔들림은 무작위 떨림이 아니라 타격 방향으로 한 번 밀린 뒤 돌아오는 카메라 킥으로 한다. 무작위 떨림은 폭발 같은 연출에만 쓴다.
- 보고할 때 타격감은 숫자로 적는다: 히트스톱 프레임 수, 카메라 킥 세기·지속, 넉백 거리.
- 숫자는 재현과 비교를 위한 것이고, 최종 판정은 오너가 직접 눌러보고 느낀 쪽이다. 숫자가 기준을 넘었는데 오너가 차이를 못 느끼면 수치가 아니라 방식(떨림→킥, 순간이동→미끄러짐)을 의심한다.
- 상태 겹침 규칙 (2026-10-27 오너 결정, `docs/mistakes.md`에서 같은 원인 4회): 새 상태값(타이머·플래그·멈춤·화면 상태)을 만들면 ① 설정·감소·초기화 지점과 ② 기존 상태(공격 중(콤보)·점프·피격·다운·히트스톱·적끼리 겹침 밀기·게임오버·전체화면·가로세로·터치 여부)와 겹칠 때 누가 처리하는지를 표로 먼저 적고, 그 표를 director 검수 요청에 첨부한다. 캐릭터 위치나 카메라를 바꾸는 줄(`.x +=`, `.x =`, `camKick`)은 전부 찾아 새 상태 적용 여부를 확인한다. 측정에는 겹치는 조합 1개 이상, 적 2명 이상 경우, 폰이 아닌 터치 기기 1개를 넣는다.
- 디버그 키는 계속 유지한다: `F` 타격감 normal↔heavy 강제 전환, `G` 0.25배속, `H` 판정 범위 표시, `M` 타격음 켜기/끄기. 기존 조작 키(방향키·WASD·Z·J·X·K·Enter)와 겹치지 않는다.

## 5. 범위
현재 있는 것(적 2종 원귀·도깨비, 웨이브 3개, 점프)은 유지한다. 오너가 결정해 새로 허용한 것:
- 점프 공격 1종 (피니시 타격감 공유)
- 쓰러진 적 추가타 1회
- 잡아 던지기 1종 (2026-10-27 오너 결정: 적에게 붙어 앞으로 밀면 잡기, 잡은 상태 Z 무릎치기, 점프 버튼 던지기)
- 코드로 합성한 타격음 1종 (에셋 파일 없이 WebAudio로 생성, `M` 키로 토글) — "소리 없이도 손맛이 나는가"를 비교 판정하기 위한 장치. 5단계 판정(소리가 있으면 손맛이 더 남) 뒤 기본 켜짐으로 변경 (2026-10-27 오너 결정)
- 코드로 합성한 효과음 몇 종: 휘두름·잡기·던진 적 착지·적 쓰러짐 (2026-10-27 오너 결정)
- 타격 진동 1종 (2026-10-27 오너 요청: 휴대폰 진동, 기본 꺼짐, 별도 버튼. 안드로이드만)
- 조선 퇴마전 세계관 시각 전환 P0 (2026-10-27 오너 지시): 그림·배경·글자만 바꾼다. 전투 로직·타격감·콤보·잡기·적 AI 는 그대로
- 벽사검 사거리 확장 (2026-10-27 오너 결정, 브랜치 `joseon-sword-reach`): 칼끝까지 명중, 3타는 칼 찌르기, 적 예고 거리·돌진을 사거리에 맞춤. 히트스톱·넉백·콤보 리듬·잡기는 그대로 (상세 `docs/sword-reach.md`). 2026-10-28 마무리 — 전투 판정·밸런스 변경 종료
- P1 정식 캐릭터 스프라이트 시범 (2026-10-28 오너 지시, 브랜치 `joseon-p1-sprites`): 윤무겸 11칸(서기·걷기 4·준비·1타·2타·3타 전용 준비·찌르기·회수) + 도깨비 4칸(공격 예고·펀치·서기·걷기) 시안을 `data/sprites.js` 로 끼워 전투 화면 비교, 윤무겸 2칸 2px 시험(`docs/p1-density.md`). 시안은 구조·규격 검증용이고 정식 아트는 픽셀 아티스트 의뢰. **정식 규격 2px 확정**(64×64 칸·scale 2·키 약 110px·칼끝 56px, 판정 57 유지 — 2026-10-28 오너 승인), 최종 명세서 `docs/p1-art-commission-spec.md`, 윤무겸 샘플 6칸 발주 자료 `docs/p1-commission/` (계약·비용 지출은 오너 승인 뒤). 코드 시안으로 나머지 칸을 더 만들지 않는다. 3타 전용 준비·회수 칸 이름만 추가(그림만 바뀜). 공격 프레임·데미지·히트스톱·넉백·실제 이동 좌표·판정은 그대로 (상세 `docs/p1-pilot.md`)

## 6. 오너에게 보고하는 방식
- 오너는 비개발자다. 코드 설명 대신 "무엇이 바뀌었고, 화면에서 어떻게 느껴지고, 오너가 무엇을 눌러보거나 정해야 하는지"로 쓴다.
- 결론 먼저, 3~5줄. 선택이 필요하면 선택지 2~3개 + 추천 1개.
- 출발값을 바꿨으면 바꾼 값과 이유를 적는다.
- 오너가 터미널에 쳐야 할 명령이 있으면 복사해서 바로 칠 수 있게 코드블록으로 준다.
- 오너가 내린 결정은 `docs/decisions.md`에 날짜와 함께 한 줄로 남긴다.
- 문서의 숫자·사실을 고칠 때는 그 값(px·칸·프레임·파일명·옛 방식 이름)을 저장소 전체에서 검색해, 같은 값을 말하는 모든 줄을 한 커밋에 함께 고친다(옛 기록으로 남길 줄은 "→ 몇 절" 표시). 보고와 director 검수 요청에 "고친 줄 수 / 검색된 줄 수"를 적는다 (2026-10-28 오너 지시, `docs/mistakes.md` 같은 원인 4회).
- 보고할 때마다 `docs/progress.md`를 갱신한다 (현재 단계 / 막힌 것 / 다음 할 일).
- 단계가 끝날 때마다 git 커밋한다. 커밋 메시지에 단계 이름을 넣는다. 오너가 "○단계 상태로 되돌려"라고 하면 이 커밋으로 되돌린다.
- 오너 보고에는 디렉터 검수 결과(통과/지적 몇 개, 반영한 것, 반영 안 한 것과 이유)를 3줄 이내로 함께 적는다.

## 7. 역할과 검수 흐름
- 메인 세션 = 게임기획자(실무자). 기획·계획·구현·측정을 직접 한다.
- `director` 서브에이전트 = 선임 게임기획자이자 디렉터(검수자). 코드를 고치지 않고 읽고 판정만 한다. 정의는 `.claude/agents/director.md`.
- 단계마다 순서는 고정이다: ① 구현 ② 자체 측정 ③ director 검수 요청 ④ 지적 반영(반영하지 않는 지적은 이유를 남긴다) ⑤ 필요하면 재검수 ⑥ 커밋 ⑦ 오너 보고 후 멈춤.
- director 검수 없이 오너에게 "완료"라고 보고하지 않는다.
- director에게 넘길 것: 이번 단계 지시 내용, 바꾼 파일과 값(전/후), 측정 결과, 스스로 의심되는 점.
- director가 "오너 판단 필요"로 분류한 항목은 실무자가 결정하지 않고 오너 보고에 선택지 + 추천으로 올린다.

## 8. 실패·실수 기록 (같은 실수를 반복하지 않기 위한 장치)
- 기록 파일: `docs/mistakes.md`. 작업 시작 시 CLAUDE.md·progress.md와 함께 반드시 읽는다.
- 기록 대상
  - 실수: 내가 만든 버그, 지시·범위 위반, 사실과 다른 보고, 측정 누락
  - 실패: 시도했지만 목표 수치나 오너 기대에 못 미친 결과
  - director 지적 중 "이전에 이미 지적됐던 것"이 다시 나온 경우 (반복 표시)
- 항목 형식 (한 항목 5줄 이내):
  ```
  ## YYYY-MM-DD · ○단계 · 실수|실패|반복
  - 무엇: 
  - 원인: 
  - 어떻게 발견: (자체 측정 / director / 오너)
  - 재발 방지 규칙: (다음부터 무엇을 먼저 확인하는지, 한 문장)
  ```
- 같은 원인이 2번 기록되면, 그 재발 방지 규칙을 이 CLAUDE.md의 해당 섹션으로 올리자고 오너 보고에 제안한다 (직접 고치지 않는다).
- 작업 전 점검: 이번 단계와 관련된 재발 방지 규칙을 먼저 찾아 읽고, 보고에 "적용한 재발 방지 규칙"을 한 줄로 적는다.
