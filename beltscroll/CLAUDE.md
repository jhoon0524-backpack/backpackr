# 벨트스크롤 프로젝트 — 작업 규칙

이 파일은 매 작업 시작 시 반드시 읽고 따른다. `docs/progress.md`가 있으면 함께 읽고, 거기 적힌 현재 단계부터 이어간다.

## 1. 프로젝트 한 줄 정의
브라우저에서 도는 2D 벨트스크롤 액션 게임. 1인 개발(오너는 비개발자), 클로드코드가 구현을 맡는다.
목표는 "적은 에셋으로 타격감이 좋은 게임". 콘텐츠 양보다 손맛과 일관된 룩이 우선이다.
핵심 가설: 많은 애니메이션 프레임 대신 이펙트와 타격감(히트스톱·흔들림·넉백)으로 손맛을 낼 수 있다.

## 2. 데이터와 코드의 경계
- 데이터(`data/` 아래 JSON)로 빼는 것: 캐릭터·이펙트·타격감·스테이지에 속하는 수치 전부 (생김새, 색, 크기, 속도, 체력, 데미지, 히트스톱, 흔들림, 넉백, 등장 순서 등).
- 코드에 두어도 되는 것: 입력 처리·게임 루프·충돌 알고리즘의 상수 (콤보 입력 허용 시간, 깊이 판정 허용치 등). 단 전부 `engine/config.js` 한 파일에 모은다. 다른 엔진 파일에 숫자를 직접 쓰지 않는다.
- `data/` 아래 JSON은 `import.meta.glob`으로 자동 로드한다. 스테이지 JSON이 캐릭터·이펙트 id를 참조하면 엔진은 그 id를 찾아 쓴다.
- "엔진 수정 없이 추가"의 정의: `data/`에 파일을 추가·수정하는 것만으로 새 적·새 이펙트가 게임에 나타나는 상태. 엔진 수정이 필요하면 이유를 먼저 보고한다.

## 3. 폴더 구조
```
data/characters/      캐릭터 정의 (파츠, 팔레트, 히트박스, 동작별 키프레임)
data/effects/         이펙트 정의 (파티클 수·수명·속도·색·형태)
data/feel/            타격감 정의 (히트스톱 프레임, 화면 흔들림, 넉백 거리)
data/stages/          스테이지·적 등장 순서
data/_reference/      기준 에셋 원본 — 읽기 전용, 오너 확인 없이 수정 금지
  look.png            오너가 고른 룩 시안 (모든 룩 비교의 기준)
  SCHEMA.md           JSON 규격 정리
engine/               렌더러·게임 루프·충돌 처리
engine/config.js      코드 쪽 상수를 모아두는 유일한 파일
tools/snap.js         장면을 PNG로 찍는 검수 스크립트
snaps/                snap 결과물 (검수용, git 제외)
docs/decisions.md     오너가 내린 결정 기록
docs/progress.md      현재 단계·막힌 것·다음 할 일
```

## 4. 바리에이션 규칙 (스타일 일관성의 핵심)
- 새 적·새 이펙트는 0부터 만들지 않는다. `data/_reference/`의 기준 JSON을 복제해서 시작한다.
- 복제본에서 바꿔도 되는 값: 팔레트, 크기 비율, 속도, 개수, 틴트, 수명, 데미지·체력 수치, 타격감 수치.
- 바꾸면 안 되는 것: 구조(파츠 구성, 키프레임 구조, 이펙트 레이어 순서, 필드 이름). 구조를 바꿔야 하면 "새 기준 에셋 후보"로 보고하고 오너 확인을 받는다.
- 적 바리에이션은 팔레트 스왑 + 수치 조정이 기본이다.

## 5. 자기 검수 루프 (이펙트·캐릭터·타격감을 만들거나 고칠 때마다)
snap은 항상 결정적으로 찍는다: 같은 장면·프레임·시드면 같은 PNG가 나와야 한다. 랜덤 때문에 결과가 바뀌면 검수가 아니다.

1. JSON 수정
2. 대상에 맞는 snap 실행
   - 생김새·이펙트 모양: `npm run snap -- <장면> <프레임>` → PNG 1장
   - 타격감: `npm run snap:strip -- <장면>` → 타격 전 2프레임~후 10프레임, 12칸 콘택트 시트 PNG + 프레임별 수치 로그(JSON)
3. 확인
   - 룩: `data/_reference/look.png`와 비교해 같은 게임으로 보이는지, 형태가 깨지지 않았는지
   - 색: snap이 출력하는 "팔레트 밖 색 개수"가 0인지 (외곽선 안티에일리어싱 중간색은 ±8 오차 허용)
   - 타격감: 이미지가 아니라 수치 로그로 판정 (히트스톱 프레임 수, 흔들림 최대 진폭, 넉백 거리)
4. 기준에 못 미치면 2로 돌아간다. 최대 3회. 3회 안에 안 맞으면 멈추고 무엇이 안 맞는지 보고한다.
5. 통과하면 오너에게 PNG와 핵심 수치를 함께 보고한다.

## 6. 범위 밖 (오너가 풀기 전까지 만들지 않는다)
- 스토리·대사·컷신
- 레벨업·장비·인벤토리 같은 RPG 성장 시스템
- 플레이어 캐릭터 2명 이상
- 스테이지 2개 이상
- 사운드 (단, 효과음 자리만 데이터에 비워둔다)

## 7. 오너에게 보고하는 방식
- 오너는 비개발자다. 코드 설명 대신 "무엇이 됐고, 화면에서 어떻게 보이고, 오너가 무엇을 눌러보거나 정해야 하는지"로 쓴다.
- 결론 먼저, 3~5줄. 선택이 필요하면 선택지 2~3개 + 추천 1개.
- 오너가 터미널에 쳐야 할 명령이 있으면 복사해서 바로 칠 수 있게 코드블록으로 준다.
- 오너가 내린 결정은 `docs/decisions.md`에 날짜와 함께 한 줄로 남긴다.
- 보고할 때마다 `docs/progress.md`를 갱신한다 (현재 단계 / 막힌 것 / 다음 할 일).
- 단계가 끝날 때마다 git 커밋한다. 커밋 메시지에 단계 이름을 넣는다 (예: "2단계: 룩 시안 3종"). 오너가 "○단계 상태로 되돌려"라고 하면 이 커밋으로 되돌린다.
