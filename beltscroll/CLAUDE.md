# Belt Brawl — 작업 규칙

이 파일은 매 작업 시작 시 반드시 읽고 따른다. `docs/progress.md`가 있으면 함께 읽고, 거기 적힌 현재 단계부터 이어간다.

## 1. 프로젝트 한 줄 정의
브라우저에서 도는 2D 벨트스크롤 액션 게임 "Belt Brawl". 1인 개발(오너는 비개발자), 클로드코드가 구현을 맡는다.
이미 플레이 가능한 버전이 있다 (웨이브 3개, 적 2종 thug·brute, 3연타, 점프, HUD, 터치 조작, art.js 픽셀 아트).
지금 목표는 기능 추가가 아니라 "손맛"을 끌어올리는 것이다.

핵심 가설: 손맛 = 입력 응답(선입력·즉시 발동) × 타이밍(준비·판정·경직 프레임) × 피드백(히트스톱·흔들림·넉백·플래시·소리).
애니메이션 프레임을 늘리는 대신 이 세 축을 조정해 손맛을 낸다. 피드백만 올려서는 안 된다. 리듬(입력 응답·타이밍)이 먼저다.

## 2. 데이터와 코드의 경계 (느낌이 확정된 뒤에 옮긴다)
- 타격감 수치는 처음부터 `FEEL` 한 곳에 모은다.
- 그 외 수치(적 능력치, 웨이브, 판정 거리 등)의 파일 분리는 오너가 손맛을 확정한 뒤에 한다. 느낌이 안 정해진 수치를 먼저 옮기지 않는다.
- 새로 짜는 코드는 숫자를 여기저기 흩어 쓰지 않는다. 한 번에 전부 갈아엎지 않는다.

## 3. 바리에이션 규칙 (스타일 일관성)
- 새 적·새 이펙트는 0부터 만들지 않는다. 기존 것(thug, brute, 기존 이펙트)을 복제해서 시작한다.
- 복제본에서 바꿔도 되는 값: 팔레트, 크기 비율, 속도, 개수, 틴트, 수명, 데미지·체력, 타격감 수치.
- 바꾸면 안 되는 것: art.js의 그림 구조, 픽셀 크기(ART.S), 이펙트의 구성 방식. 바꿔야 하면 이유와 함께 먼저 보고하고 오너 확인을 받는다.
- art.js에 이미 있는 포즈(예: windup)를 먼저 찾아 쓰고, 새 포즈는 꼭 필요할 때만 만든다.

## 4. 손맛 설계 규칙과 검수
- 사거리 여유 규칙: 적이 플레이어 앞에서 자연스럽게 멈추는 거리와 약공격 사거리 사이에 8px 이상 여유를 둔다. 제자리 연타가 헛스윙하면 버그다.
- 넉백은 비율이 아니라 역할로 정한다: 약공격은 적이 다음 타 사거리 안에 남는 거리, 피니시(3타·점프 공격·사망 타격)는 확실히 날아가는 거리.
- 흔들림은 무작위 떨림이 아니라 타격 방향으로 한 번 밀린 뒤 돌아오는 카메라 킥으로 한다. 무작위 떨림은 폭발 같은 연출에만 쓴다.
- 보고할 때 타격감은 숫자로 적는다: 히트스톱 프레임 수, 카메라 킥 세기·지속, 넉백 거리.
- 숫자는 재현과 비교를 위한 것이고, 최종 판정은 오너가 직접 눌러보고 느낀 쪽이다. 숫자가 기준을 넘었는데 오너가 차이를 못 느끼면 수치가 아니라 방식(떨림→킥, 순간이동→미끄러짐)을 의심한다.
- 디버그 키는 계속 유지한다: `F` 타격감 normal↔heavy 강제 전환, `G` 0.25배속, `H` 판정 범위 표시, `M` 타격음 켜기/끄기. 기존 조작 키(방향키·WASD·Z·J·X·K·Enter)와 겹치지 않는다.

## 5. 범위
현재 있는 것(적 2종, 웨이브 3개, 점프)은 유지한다. 오너가 결정해 새로 허용한 것:
- 점프 공격 1종 (피니시 타격감 공유)
- 쓰러진 적 추가타 1회
- 코드로 합성한 타격음 1종 (에셋 파일 없이 WebAudio로 생성, 기본 꺼짐, `M` 키로 토글) — "소리 없이도 손맛이 나는가"를 비교 판정하기 위한 장치

아래는 오너가 풀기 전까지 만들지 않는다.
- 적 종류·웨이브 추가
- 사운드 에셋·배경음악 (위 합성 타격음 1종 제외)
- 스토리·대사·컷신
- 레벨업·장비·인벤토리 같은 RPG 성장 시스템
- 플레이어 캐릭터 2명 이상, 스테이지 2개 이상

## 6. 오너에게 보고하는 방식
- 오너는 비개발자다. 코드 설명 대신 "무엇이 바뀌었고, 화면에서 어떻게 느껴지고, 오너가 무엇을 눌러보거나 정해야 하는지"로 쓴다.
- 결론 먼저, 3~5줄. 선택이 필요하면 선택지 2~3개 + 추천 1개.
- 출발값을 바꿨으면 바꾼 값과 이유를 적는다.
- 오너가 터미널에 쳐야 할 명령이 있으면 복사해서 바로 칠 수 있게 코드블록으로 준다.
- 오너가 내린 결정은 `docs/decisions.md`에 날짜와 함께 한 줄로 남긴다.
- 보고할 때마다 `docs/progress.md`를 갱신한다 (현재 단계 / 막힌 것 / 다음 할 일).
- 단계가 끝날 때마다 git 커밋한다. 커밋 메시지에 단계 이름을 넣는다. 오너가 "○단계 상태로 되돌려"라고 하면 이 커밋으로 되돌린다.
- 오너 보고에는 디렉터 검수 결과(통과/지적 몇 개, 반영한 것, 반영 안 한 것과 이유)를 3줄 이내로 함께 적는다.

## 7. 역할과 검수 흐름
- 메인 세션 = 게임기획자(실무자). 기획·계획·구현·측정을 직접 한다.
- `director` 서브에이전트 = 선임 게임기획자이자 디렉터(검수자). 코드를 고치지 않고 읽고 판정만 한다. 정의는 `.claude/agents/director.md`.
- 단계마다 순서는 고정이다: ① 구현 ② 자체 측정 ③ director 검수 요청 ④ 지적 반영(반영하지 않는 지적은 이유를 남긴다) ⑤ 필요하면 재검수 ⑥ 커밋 ⑦ 오너 보고 후 멈춤.
- director 검수 없이 오너에게 "완료"라고 보고하지 않는다.
- director에게 넘길 것: 이번 단계 지시 내용, 바꾼 파일과 값(전/후), 측정 결과, 스스로 의심되는 점.
- director가 "오너 판단 필요"로 분류한 항목은 실무자가 결정하지 않고 오너 보고에 선택지 + 추천으로 올린다.

## 8. 실패·실수 기록 (같은 실수를 반복하지 않기 위한 장치)
- 기록 파일: `docs/mistakes.md`. 작업 시작 시 CLAUDE.md·progress.md와 함께 반드시 읽는다.
- 기록 대상
  - 실수: 내가 만든 버그, 지시·범위 위반, 사실과 다른 보고, 측정 누락
  - 실패: 시도했지만 목표 수치나 오너 기대에 못 미친 결과
  - director 지적 중 "이전에 이미 지적됐던 것"이 다시 나온 경우 (반복 표시)
- 항목 형식 (한 항목 5줄 이내):
  ```
  ## YYYY-MM-DD · ○단계 · 실수|실패|반복
  - 무엇: 
  - 원인: 
  - 어떻게 발견: (자체 측정 / director / 오너)
  - 재발 방지 규칙: (다음부터 무엇을 먼저 확인하는지, 한 문장)
  ```
- 같은 원인이 2번 기록되면, 그 재발 방지 규칙을 이 CLAUDE.md의 해당 섹션으로 올리자고 오너 보고에 제안한다 (직접 고치지 않는다).
- 작업 전 점검: 이번 단계와 관련된 재발 방지 규칙을 먼저 찾아 읽고, 보고에 "적용한 재발 방지 규칙"을 한 줄로 적는다.
