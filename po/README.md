# PO 에이전트 — 파일 구조와 SSOT 규칙

## 원칙

같은 사실이 두 곳에 적혀 있으면 반드시 한쪽이 뒤처진다.
모든 정보는 소유자가 한 곳뿐이고, 나머지는 참조한다.

## 층 구조

```
.claude/skills/            ← Claude Code가 이 경로에서만 스킬을 읽는다. 여기 있는 것이 정본
├── prd/SKILL.md
├── prd-review/SKILL.md
├── backlog/SKILL.md
└── validate/SKILL.md

po/context/
├── po-principles.md       ← 모든 스킬이 공유하는 판단 원칙. 소유자: PO
├── org.md                 ← 조직 구성. 소유자: PO
├── stack.md               ← 기술 스택. 소유자: BE/FE 리드
├── metrics.md             ← 지표 사전. 소유자: PO
└── decisions.md           ← 결정 로그. 사람만 쓴다

outreach/                  ← PO 업무가 아닌 스킬. 스킬 경로 밖이라 로드되지 않는다
strategy/                  ← strategy-doc. 범위 밖이나 폐기는 아니다
```

미편입: `plan-review` · `weekly-report` · `problem-discovery` · `diagnosis` · `okr`.
파일이 아직 없다. 가져와서 원칙 참조를 붙이고 경계를 확인한다.

폐기: `strategy-review` (2026-08-02). 되살리지 않는다.

## 정본은 검사 가능해야 한다

선언만으로는 갈라진다. 개인 스킬과 어긋났는지 확인:

```
po/check.sh
```

| 출력 | 뜻 |
|---|---|
| `같음` | 정본과 개인본이 일치 |
| `다름` | 개인본이 정본과 다르다 → 개인본을 지운다 |
| `미편입` | 직접 만든 스킬인데 정본에 없다 → 편입하거나 지운다 |
| `레포만` | 정본에만 있다 (정상) |

기본 제공 스킬(`docx`·`pdf` 등)은 `manifest.json`의 `source`로 걸러진다.
무시 목록을 손으로 관리하지 않는다 — 그 목록이 또 갈라진다.

CI에는 넣지 않는다. 이 검사는 개인 환경의 설치본을 보는 것이라 러너에서는 항상 통과한다.
CI가 의미를 갖는 건 오케스트레이터가 들어와 라우팅 테이블을 검사할 때다.

## 정보별 소유자

| 정보 | 소유자 | 스킬의 접근 방식 |
|---|---|---|
| 서비스 정책 (수수료·상태머신·계산식·Enum) | Notion 서비스 정책 문서 트리 | 실행 시 MCP로 조회 |
| 조직 구성 | `po/context/org.md` (소유자 PO) | 파일 읽기 |
| 기술 스택 | `po/context/stack.md` (소유자 BE/FE 리드) | 파일 읽기 |
| 공통 판단 원칙 | `po/context/po-principles.md` | 파일 읽기 |
| 지표 정의 | `po/context/metrics.md` | 파일 읽기 |
| 스킬 고유 절차·출력 형식 | 각 SKILL.md | 자체 보유 |
| 제품 백로그·로드맵 | Drive 로드맵·백로그 시트 | 조회는 자유, 수정은 사람이 반영 |
| 이슈·Epic 상세 | Jira (backpackr.atlassian.net) | 조회 |
| 개별 프로젝트 상태·결정 | 전략 문서 (`strategy/strategy-doc`) | 해당 스킬 경유 |

산출물(PRD 등)의 정본은 Notion이다. 입력은 레포, 산출물은 노션.

## 정책 층 — 로컬 md와 Notion의 관계

Notion 도메인 문서 하단의 "코드 정합 검증" 콜아웃에 로컬 그라운딩 문서의 경로가 있다.
`docs/domain-overview/03-project.md`, `docs/domain-overview/06-settlement.md` 형태이며
**이 저장소가 아닌 다른 저장소에 있다.** 문서끼리 서로를 부를 때도 이 파일명을 쓴다.

**\[확인 필요\]** 갱신 주기·갱신 주체, 그리고 어느 저장소인지.

- 로컬 md = 코드 대조로 생성되는 **파이프라인 산출물**. 사람이 직접 고치지 않는다
- Notion = 사람이 읽고 정책을 **확정하는 면**. 스킬이 조회하는 대상
- 방향은 로컬 → Notion 단방향. Notion에서 PO가 확정한 내용은
  다음 재생성 때 로컬로 되먹임되어야 하며, 그 되먹임 절차가 없으면 드리프트가 생긴다
- 스킬은 **Notion만 본다.** 로컬 md를 직접 읽지 않는다.
  로컬을 읽기 시작하면 SSOT가 둘이 된다

## 검토 스킬의 경계

이름이 비슷해 헷갈리기 쉬우므로 축으로 가른다.

| 스킬 | 대상 | 시점 | 무엇을 보나 |
|---|---|---|---|
| `prd` Step 0-A | 쓰려는 기획 | 쓰기 전 | 기존 문서와의 충돌·중복 |
| `prd` Step 2 | 내 PRD 초안 | 쓰는 중 | 자가 점검 |
| `prd-review` | 완성된 PRD | 개발 착수 전 | 스펙 완결성·내부 정합성 |
| `validate` | 분석·인사이트·보고서 | 공유 전 | 데이터 주장의 타당성 |
| `plan-review` | 팀원이 쓴 문서 | 피드백 시 | 숫자 → 판 2패스 (미편입) |

`validate`에 PRD를 넣지 않는다. 6개 항목이 데이터 주장을 겨냥한 축이라
상태머신 데드락이나 스펙 부재를 잡지 못한다.

## 소관을 옮긴 스킬

PO 업무가 아니라 위치만 옮겼다. 기능은 손대지 않았다.

| 스킬 | 위치 | 실제 소관 | 이유 |
|---|---|---|---|
| `creator-trend-newsletter` | `outreach/` | 아웃리치 | 창작자 발송물 제작. PO 산출물이 아니다 |
| `tumblbug-trend-roulette` | `outreach/` | 아웃리치 · 마케팅 | 키워드 시장 조사 아티팩트 |
| `gmv-dashboard-update` | `outreach/` | 운영 · 데이터 | 대시보드 수치 갱신. 판단이 없는 기계 작업 |
| `strategy-doc` | `strategy/` | 전략 | 범위 밖이지만 소유자 표의 한 행을 맡고 있어 폐기하지 않았다 |

## 해소한 라우팅 충돌

- `validate` 설명과 본문에 **PRD는 대상이 아니며 `prd-review`로 간다** 명시
- `backlog`가 백로그 순서(Total 규칙) 소관. `strategy-review`는 폐기됐으므로
  "우선순위 정해줘" 트리거의 경합 상대가 없다

## 스킬 중복 정리 기준

- 두 스킬이 같은 판단을 하면 하나를 다른 하나의 하위 단계로 흡수한다
- 아웃리치와 공유하는 스킬(`validate`·`weekly-report`)은
  한쪽에만 원본을 두고 다른 쪽이 참조한다. 복제 금지
- PO 업무와 무관한 스킬은 이 트리에서 뺀다

## 새 스킬을 추가할 때 확인할 것

1. 기존 스킬의 하위 단계로 들어갈 수 있는가 — 그렇다면 새로 만들지 않는다
2. 정책 수치를 자체 보유하려 하는가 — 금지. Notion 조회로 처리한다
3. 조직·기술 정보를 인라인으로 적으려 하는가 — 금지. `po/context/org.md` · `stack.md` 참조
4. 공통 판단 원칙을 다시 적으려 하는가 — 금지. `po/context/po-principles.md` 참조.
   이 스킬에만 해당하는 절차인지 모든 스킬에 해당하는 원칙인지 먼저 가른다
5. PO 오케스트레이터 라우팅에 어느 요청 유형이 이 스킬로 오는지 정의했는가
