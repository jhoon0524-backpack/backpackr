## 0. 먼저 답이 필요한 것 (R2)

목적을 둘 중 하나로 골라야 다음 일의 순서가 정해진다.

- **A. 답이 정본에서 나오게 한다** (질문 → 정본 → 답, 결정이 바뀌면 정본도 바뀜) → 다음 일은 **갱신 루프 + DRI 지정**
- **B. AI가 전사 문서를 읽을 수 있게 정리한다** (접근성) → 다음 일은 **워크스페이스 정리·권한**

조사해 보니 A의 절반은 이미 돌아가고 있다(§3). 그래서 A를 추천한다. B로 가더라도 아이디어스 혼입 문제 하나만 따로 풀면 된다.

## 3. 이미 있는 것 (새로 만들지 말 것)

조사 중 확인한, 브리프의 "갱신 루프" 절반에 해당하는 것들.

1. **블벅이** — 슬랙 봇. 노션 정본을 `policy-mirror/`로 미러링해 읽고 답한다. 코드는 bitbucket `backpackr/tbb-po` → `tools/blbugi/`. 답변에 출처 페이지와 "문서 간 상충" 경고를 붙인다. 예: 9/10 운영셀 질문에 "프로젝트 생애주기 문서와 창작자 권한 문서가 어긋난다, New/Old 두 체계가 남아 있어 담당자 확인 필요"라고 답함.
2. **정책 원본 변경 감지** — 9/10 Khan 자신에게 온 DM. 노션 정책 페이지 변경을 감지해 "미러 갱신 검토 필요"를 알린다. 단, 이건 "변했다"만 알지 "정본이 결정과 어긋난다"는 못 잡는다.
3. **PRD → 노션 정책 문서 업데이트 도구** — 9/10 CTO 메시지: "프로젝트 완료 후 prd to notion 정책 문서 업데이트 호출해서 싱크 안 한 분은 해달라. 시간 나면 자동 갱신으로 수정하겠다." 즉 결정 → 정본 반영 경로가 이미 있고, 안 지켜지는 게 문제다.
4. **텀블벅 팀 위키** (`3a41f5a7-1344-818b-a974-fbff1050145f`) — 소스 DB → 위키 DB → 주 1회 ingest, DRI 1명 구조. 운영 규칙에 "DRI: [지정 필요]"가 비어 있다. 브리프 3항의 갱신 루프는 이 틀을 그대로 쓰면 된다.

따라서 갱신 루프에서 **없는 것은 딱 두 개**: 도메인별 DRI 이름, 그리고 "결정 → 6번 칸 한 줄" 규칙.

## 4. 기준선 측정 방법 (제안)

- 04 파일의 44건 중 사람이 답을 남긴 23건을 정답지로 삼는다.
- 같은 질문을 블벅이에게 다시 물어 "정본만으로 맞게 답한 비율"을 잰다. 지금 블벅이가 이미 답한 21건은 정답 대조가 안 된 상태라 이 숫자는 아직 없다.
- 양식 적용·빈칸 해소 후 같은 44건으로 다시 잰다. 문서 수가 아니라 이 비율이 지표.

## 5. 관찰 (작업팀에 전달할 것)

- **팬콜**은 질문 4건 모두 "기준 문서 없음"으로 끝났다. 12개 도메인 어디에도 팬콜 페이지가 없다. 운영셀은 "아웃리치셀이 기준을 정해주면 참고"라고 답함 → DRI 후보가 애매한 도메인.
- 같은 규칙을 두 경로로 중복 질문한 사례 3건(후기 PICK 기준, 팬콜 구성, 피싱 대응). 정본이 있었으면 한 번으로 끝났을 질문.
- 코드에만 있는 규칙이 많다. 후기 평점 노출 기준(만족 50%), 홈 '신규' 탭 정렬 등은 블벅이가 "문서엔 없고 앱 코드 기준"으로 답했다. 예시 페이지(03)의 근거 칸이 이걸 드러내는 용도.
- 정산 페이지의 R8(결제 수수료는 텀블벅 수익계좌로 안 감)은 "2026-06-08 재무회계셀 결정"이라고만 적혀 있고 회의록 링크가 없다. 6번 칸(변경 이력)이 필요한 전형적 사례.
