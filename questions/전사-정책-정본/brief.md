## 3. 방향 (제안, Khan 이견 없었음)
- 핵심은 문서 생산이 아니라 **정본이 썩지 않게 하는 갱신 루프**
- 구조 3층: ① 인덱스(질문→도메인 라우팅표) ② 도메인별 정본(동일 양식) ③ 근거(코드·결정 기록·변경 이력). 현재는 ②만 있고 ①③ 약함
- 전사 확장 순서: 서비스 정책(텀블벅→아이디어스 같은 틀) → 운영 규정(CS 응대·심사 기준) → 사내 규정(HR·경비)
- 갱신 루프: "정책 변경 결정 = 정본 페이지 수정" 규칙 + 도메인별 DRI 1명 + 주 1회 에이전트가 최근 PRD·지라·슬랙 결정을 훑어 정본과 어긋나는 걸 DRI에게 올리는 스캔 (기존 위키 주간 ingest 방식 재사용, 새로 만들지 않음)
- 성과 지표: 문서 수가 아니라 "샘플 질문 N개 중 정본만으로 맞게 답한 비율". 시작 전 기준선 측정

## 4. 도메인 정본 양식 (확정 — 작업팀 요청으로 만듦)
페이지 하나 = 도메인 하나. 칸 6개, 더 늘리지 말 것.
1. **한 줄 정의** — 다루는 범위 / 안 다루는 범위 (e.g "정산: 성공 확정 후 창작자에게 돈이 가는 규칙. 결제 승인·취소는 결제 페이지")
2. **용어** — 헷갈리는 단어만 (e.g "결제 반영 금액 = 취소 제외 후 금액")
3. **규칙** — 번호 붙여 한 줄씩, "~이면 ~한다" 형태. 숫자·기한·비율은 숫자로
4. **예외·엣지** — 규칙이 안 통하는 경우와 처리
5. **근거·출처** — 코드 파일명 / 결정 회의·PRD 링크 / 법령. 모르면 `[확인 필요: 담당자]`로 비움. 지어내지 않음
6. **변경 이력** — 날짜 / 바뀐 규칙 번호 / 결정자. 여기 한 줄 추가가 곧 결정 기록

페이지 속성 3개: DRI · 최종 확인일 · 상태(초안/확정/폐기)
기존 도메인 문서 구조("핵심 비즈니스 정책 / 기능별 정책 및 예외사항")와 거의 같으므로 갈아엎지 말고 5·6번 칸만 추가해 맞춤.
