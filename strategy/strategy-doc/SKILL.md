# 전략 문서 갱신 스킬 (strategy-doc)

`context/po-principles.md`를 먼저 읽고 그 원칙 위에서 실행한다.

**기능 스펙은 여기 쓰지 않는다.** 워크스트림 문서(예: 상시판매.md)와
Notion PRD DB가 같은 주제를 다룰 수 있는데, 전략 판단·옵션·가정은 이쪽,
기능 요구사항과 인수조건은 PRD DB로 간다.

전략 대화는 휘발되고 사고는 축적돼야 한다. 이 스킬은 대화의 결과물을 레이어 구조의 전략 문서에 반영한다. 핵심 원칙 세 가지:

1. **append가 아니라 rewrite** — 대화 로그를 쌓지 않는다. "지금까지의 결론 상태"를 덮어쓴다.
2. **AI는 제안하고 인간이 커밋한다** — 결정(Decisions) 섹션은 사용자가 명시적으로 지시했을 때만 쓴다.
3. **갱신 전 diff, 갱신 후 확인** — 파일을 먼저 고치지 않는다. 변경안을 보여주고 승인받는다.

---

## 문서 구조 (전제)

전략 문서는 3개 레이어로 구성된다. 저장 위치는 사용자 레포(예: `maeculbunseog/strategy/`) 또는 사용자가 지정한 디렉토리.

```
strategy/
├── CORE.md                  # Layer 1: 구조적 진단·승부처 (수년 단위, 거의 불변)
├── 2026H2-outreach.md       # Layer 2: 워크스트림별 (분기 단위)
├── 상시판매.md
├── 만들어주세요.md
└── archive/                 # Layer 3: 종료된 워크스트림 (회고 붙여 박제)
    └── 2026Q2-outreach.md
```

### Layer 2 문서의 5섹션 구조

모든 워크스트림 문서는 아래 구조를 따른다. 새 문서를 만들 때도 이 템플릿을 쓴다.

```markdown
# {워크스트림 이름}

> CORE 연결: {CORE.md의 어떤 진단/승부처에 걸려 있는지 한 줄}
> 상태: 활성 | 보류 | 종료예정
> 최종 갱신: YYYY-MM-DD

## 1. 현황 (Facts)
데이터로 확인된 사실만. 출처와 기준일 명시.

## 2. 옵션 공간 (Options)
검토한 선택지. 채택/보류/폐기 상태와 함께, **폐기한 이유를 반드시 남긴다.**

## 3. 핵심 가정 (Assumptions)
현재 방향이 성립하려면 참이어야 하는 것들.
각 가정에 [검증됨 YYYY-MM-DD] / [미검증, 등록 YYYY-MM-DD] 표시.

## 4. 결정 (Decisions)
인간이 커밋한 것만. 날짜 + 결정 내용 + (있으면) 근거 한 줄.

## 5. 열린 질문 (Open Questions)
다음 세션에서 공격할 지점.
```

## 모드 1: 갱신 ("정리해", "반영해")

### 1단계 — 대상 파일 판단

`strategy/` 디렉토리의 파일 목록을 읽고, 이번 대화가 어느 워크스트림에 속하는지 판단한다.

- 명확하면 해당 파일 진행.
- 두 개 이상 워크스트림에 걸치면: 각각의 델타를 분리해서 파일별로 처리.
- 어느 파일에도 안 속하면: "새 워크스트림 문서를 만들까요, 아니면 기존 파일 중 하나에 넣을까요?" 질문. 마음대로 새 파일을 만들지 않는다.
- 구조적 진단 수준의 내용(플랫폼 전체 문제 정의, 승부처 변경)이면 CORE.md 후보. 단, **CORE.md 변경은 항상 별도로 강조해서 승인받는다** — CORE 변경은 갱신이 아니라 피벗이다.

### 2단계 — 현재 상태 읽기

대상 파일의 현재 내용을 전부 읽는다. 파일이 없으면 위 템플릿으로 신규 생성을 제안한다.

### 3단계 — 델타 추출

이번 대화에서 발생한 변화만 추출한다. 대화 요약이 아니다. 섹션별로:

| 섹션 | 추출 기준 |
|---|---|
| 현황 | 새로 확인된 사실, 기존 수치의 갱신. 추측·해석은 제외 |
| 옵션 | 새로 검토된 선택지, 상태가 바뀐 선택지(채택→폐기 등). 폐기면 이유 필수 |
| 가정 | 새로 드러난 가정, 검증 상태가 바뀐 가정 |
| 결정 | **사용자가 "결정으로 기록해"라고 명시한 것만.** 대화 중 동의("좋네", "그래")는 결정이 아니다 |
| 열린 질문 | 새로 생긴 질문, 답변돼서 닫힌 질문 |

델타가 없는 섹션은 건드리지 않는다. 델타가 아예 없으면 "반영할 변화가 없습니다"라고 말하고 끝낸다. 억지로 갱신하지 않는다.

### 4단계 — 섹션별 권한에 따라 처리

| 섹션 | 권한 | 처리 |
|---|---|---|
| 현황, 열린 질문 | 자동 갱신 가능 | diff에 포함시키되 "자동 반영 예정"으로 표시 |
| 옵션, 가정 | 승인 필요 | diff 보여주고 승인 대기 |
| 결정 | 명시 지시 필요 | 사용자가 명시하지 않았으면 diff에 넣지 않는다. 단, 대화에서 결정처럼 보이는 발언이 있었다면 "이것을 결정으로 기록할까요?"라고 별도 질문 |

### 5단계 — diff 제시 및 승인

파일을 고치기 전에 변경안을 보여준다. 형식:

```
## 📝 {파일명} 갱신안

### 자동 반영 (현황·열린 질문)
+ [현황] 신규 후원자 유입 6월 기준 전월 대비 -8% (주간 GMV 리포트, 07-01)
- [열린 질문] ~~체험단 물량 확보 가능한가~~ → 닫힘 (운영팀 확인 완료)

### 승인 필요 (옵션·가정)
+ [옵션/폐기] 라이브 옥션 조기 출시 — 폐기 사유: 개발 리소스 상시판매와 충돌
+ [가정/미검증] 상시판매 창작자의 70%가 기존 펀딩 창작자일 것

### 결정 후보 (명시 확인 필요)
? "체험단 P1로 올린다"는 발언이 있었습니다. 결정으로 기록할까요?
```

승인 응답을 받으면 파일을 갱신하고, 최종 갱신일을 업데이트하고, 갱신 완료 요약을 한 줄로 보고한다. 부분 승인("결정 부분은 빼")도 그대로 따른다.

## 모드 2: 헬스체크 ("헬스체크", "상태 보여줘")

`strategy/` 전체를 스캔해서 부패 신호를 보고한다:

1. **정체 파일**: 상태가 '활성'인데 최종 갱신이 14일 이상 지난 파일 → archive 이동 또는 갱신 제안
2. **방치된 가정**: [미검증] 상태로 28일 이상 지난 가정 → 검증 방법 제안
3. **CORE 정합성**: 각 워크스트림의 최근 결정이 CORE.md의 진단·승부처와 모순되는지 점검. 예: CORE가 "신규 유입이 핵심 문제"인데 모든 워크스트림 리소스가 기존 창작자 리텐션에 있으면 지적
4. **고아 질문**: 3회 이상 갱신을 거치며 살아남은 열린 질문 → 답할 수 없는 질문이면 폐기 제안

출력은 문제가 있는 항목만. 깨끗하면 "이상 없음" 한 줄.

---

## 모드 3: 아카이브 ("이거 종료해", "archive로 보내")

1. 대상 파일에 `## 회고` 섹션 추가를 제안 — 결과 요약 3~5줄 (목표 대비 성과, 맞았던 가정, 틀렸던 가정)
2. 회고 내용은 사용자에게 초안을 제시하고 승인받는다
3. 승인 후 `archive/`로 이동, 파일명에 기간 프리픽스 유지 (예: `2026Q2-outreach.md`)
4. CORE.md나 다른 활성 문서가 이 파일을 참조하고 있으면 링크 갱신

## 작동 원칙

**대화 요약을 넣지 않는다.** "오늘 X에 대해 논의했고..."는 금지. 상태 변화만 기록한다.

**결정의 문턱을 지킨다.** 이 스킬의 존재 이유는 문서가 인간의 커밋 기록이라는 것이다. AI가 결정을 대신 쓰기 시작하면 문서의 존재 이유가 무너진다. 애매하면 항상 묻는다.

**갱신하지 않을 용기.** 발산 중인 대화, 결론 없는 브레인스토밍은 반영하지 않는 게 맞다. "아직 발산 중이라 열린 질문 한 줄만 추가하는 게 좋겠습니다"라고 말할 수 있어야 한다.

**폐기 이유는 자산이다.** 옵션을 폐기할 때 이유 없이 지우면 3개월 뒤 같은 논의를 반복한다. 이유가 대화에 없으면 사용자에게 묻는다.

**CORE는 무겁게 다룬다.** CORE.md 수정 제안은 반드시 "⚠️ CORE 변경 — 이것은 구조적 진단의 변경입니다"라고 명시하고 별도 승인을 받는다.

**diff는 짧게.** 승인은 30초 안에 끝나야 한다. 변경안이 길어지면 섹션별로 접어서 핵심만 먼저 보여준다.
