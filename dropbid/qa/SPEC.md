# Dropbid QA 규격

## 1. 개요
- **무엇:** 배포된 Dropbid 를 사람이 쓰는 순서대로 열어 보고, 잘못된 것을 재현 절차와 함께 남긴다.
- **누가 쓰나:** 이 문서를 읽고 다음 QA 를 이어받는 사람. 그리고 고칠 개발자.
- **성공 기준:** 아래 다섯 흐름을 처음부터 끝까지 통과시키고, 통과하지 못한 지점마다
  재현 절차가 남아 있을 것. **"다 봤다" 가 아니라 "이건 봤고 이건 못 봤다" 로 끝난다.**

## 2. 핵심 흐름

QA 는 이 순서대로 돈다. 실제 사람이 겪는 순서다.

1. **구경** — 드롭 목록을 연다. 사진·현재가·남은 시간이 보인다
2. **입찰** — 상품에 들어가 입찰한다. 거부되면 이유가 화면에 뜬다
3. **판매** — 상품을 등록하고 검수 대기가 되는 것을 확인한다
4. **검수** — 운영자로 승인한다. 경매가 열린다
5. **마감** — 마감 뒤 낙찰·유찰·결제 기한 화면을 확인한다

## 3. 대상 규격
- **프로덕션:** `https://dropbid-khan-9759s-projects.vercel.app`
  (Vercel `dropbid`, 저장소 기본 브랜치 자동 배포. 배포별 주소가 아니라 **항상 최신을 가리키는** 주소다)
- **데이터:** 실제 Supabase (`watereetyukaayzbvkkt`). 시연 데이터만 들어 있다
- **사용자 전환:** 로그인이 없어 화면 오른쪽 위 선택으로 바꾼다 (쿠키 `demo_user`)
- **로컬:** 로컬 Postgres + **프로덕션 빌드**로 본다. 스키마는 프로덕션과 같다
  ```
  npm run db:reset && npm run db:seed
  npx next build && npx next start -p 3100
  ```
  `npm run dev` 로 보지 않는다 — 이 환경에서는 일부 청크가 403 이라 하이드레이션이
  안 되고, 카운트다운이 멈춘 것처럼 보여 헛발견을 한다 (실제로 겪었다)

## 4. 경계

이번 QA 에서 보지 않는 것. 없으면 범위가 계속 늘어난다.

- 카카오 로그인 (미연동)
- 실제 결제·환불 (포트원 미연동. 화면의 결제 버튼은 자리만 있다)
- 알림 실제 발송 (적재까지만 되어 있다)
- 사진 업로드 (Storage 미연동. 주소 입력으로 대신한다)
- 부하·성능, 접근성 심층 감사

## 5. 되돌릴 수 없는 지점

`CLAUDE.md` 4장과 짝을 이룬다. QA 중 이 근처에 가면 멈춘다.

- 결제 요청·환불 실행
- 알림 실제 발송
- 프로덕션 데이터 삭제·초기화
- 운영자 권한으로 남의 상품 승인·반려
