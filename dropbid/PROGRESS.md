# 현재 진행 상황

## 2026-09-01 — 화면 QA 15건 수정

브라우저로 모든 화면을 눈으로 확인해 찾은 15건을 순서대로 고치고, 고칠 때마다 다시 찍어 확인했다.

**버그**
1. 날짜가 영어로 나왔다 ("2026. 9. 2. AM 07:57까지 결제해야 합니다"). `Intl` 에 locale 을 'ko-KR' 로
   줬는데도 **Node 와 크롬의 CLDR 판본이 달라** 한쪽이 "AM" 을 냈다. 서버가 Node 라 서버 컴포넌트에서는
   영어가 그대로 굳었다. 오전/오후를 ICU 에 맡기지 않고 `lib/format.ts` 에서 직접 조립하도록 바꿨다.
   두 런타임에서 같은 문자열이 나오는 것을 확인했다 (히드레이션 불일치도 함께 사라졌다).
2. 시작가를 15,500원처럼 1,000원 단위가 아닌 금액으로 넣을 수 없었다. `type=number` 의 `step` 에 걸려
   브라우저가 **영어로** 막았고, 500원을 넣으면 "0과 1000이 가장 가깝다"며 0원을 권했다.
   금액 칸을 `app/money-input.tsx` 로 바꿔 자릿수를 보여 주고(55,000), 금액 규칙은 전부 서버가 판정한다.

**운영 구멍**
3. 검수 화면에 잠금이 없었다. 일반 판매자로 자기 상품을 자기가 승인할 수 있었다.
   `profiles.is_operator` 를 두고 화면·서버 액션·**DB 함수** 세 곳에서 막았다.
4. 드롭이 끝나면 홈이 백지가 됐다. "지난 드롭 결과" 를 붙였다.
   처음엔 회차 행의 마감 시각으로 짰다가 아무것도 안 나왔다 — 연장·운영자 개입으로 회차와 경매의
   마감 시각이 어긋난다. 실제로 마감된 경매를 기준으로 다시 짰다.
5. 유찰·미결제로 끝난 상품이 막다른 길이었다. `relist_product` 와 "같은 내용으로 다시 올리기" 를 넣었다.

**개인정보·표기**
6. 최고입찰자·낙찰자 닉네임이 비로그인에게도 그대로 보였다 → `maskNickname` (박덕후 → 박*후).
   판매자 이름은 거래 신뢰에 필요해 그대로 뒀다.
7. 입찰 0회인데 "현재가" 로 보였다 → 입찰이 없으면 "시작가" 로 쓴다.
8. 입찰가 입력칸에 자릿수 구분이 없었다 → 2번과 같은 칸으로 해결.

**안내 누락**
9. 등록 성공에 확인이 없었다 → `/me?registered=1` 배너.
10. 마이페이지 "내 입찰" 에 남은 시간이 없었다 → 진행 중인 것에 카운트다운.
11. 낙찰 항목에 결제 버튼이 없었다 → 남은 시간과 버튼을 넣었다.
    **결제 연동(포트원) 전이라 버튼은 눌리지 않게 두고 그 사실을 적었다.**
12. 마감된 경매가 "최고가" 배지로 진행 중처럼 보였다 → 낙찰/낙찰 실패/유찰/미결제 종료.
13. 비로그인에게 등록 폼이 다 열렸다 → 마이페이지와 같게 먼저 막는다.
14. 판매자가 넣은 펀딩 페이지 링크를 상세에서 안 보여 줬다 → 링크를 노출한다.
15. "상태 A" 뜻풀이가 없었다 → `CONDITION` 을 한 곳에 두고 "상태 A · 미개봉/새것".

**검증**
- 새 테스트 8개 (`__tests__/db/operator_and_relist.test.ts`). 검사 5개를 하나씩 무력화해
  **정확히 해당 테스트만 빨개지는 것**을 확인한 뒤 되돌렸다.
- `npm test` 131개 통과 / `npm run lint` / `npm run typecheck` 통과.
- 15개 화면 조합을 훑어 페이지 오류·영어 잔재("AM", "Please enter")가 없는 것을 확인했다.

**확인 못 한 것**
- 마이그레이션 2개(`20260901000100`, `20260901000200`)는 **로컬에만 적용했다.**
  Supabase 프로덕션 적용은 사람이 해야 한다 (CLAUDE.md 4장).
- 결제 버튼은 자리만 만든 것이다. 포트원이 붙기 전까지 눌리지 않는다.
- 사진은 여전히 안 보인다 (Storage 미연동). 검수 화면의 후원 인증도 주소 글자 그대로다.

## 확인하지 못한 것
여기가 이 문서에서 가장 중요하다.
확인 안 한 것을 완료로 적으면 다음 세션이 그 위에 쌓는다.
- `npm run dev` / `npm run build` 는 아직 안 돌려봤다
- **Auth·Storage·Realtime 은 이 환경에서 한 번도 안 돌려봤다.** Docker 가 되는 환경에서 확인해야 한다.
  이 셋에 의존하는 작업([기능]의 카카오 로그인·이미지 업로드, [화면]의 Realtime 갱신)은
  여기서 완료로 표시하면 안 된다
- PRD 인수 조건 9개 중 7개가 테스트로 고정됐다 (동시 입찰, 30초 연장, 후원 인증 누락 거부,
  마감 멱등, 유찰 전환, 직접 쓰기 차단, 스케줄러 실행 기록).
  결제 기한 만료까지 8개가 고정됐다. 남은 1개(낙찰·유찰 알림)는 **적재까지 고정했고 실제 발송만 남았다** —
  알림톡·이메일 키가 있어야 한다
- pg_cron 확장이 로컬에 없어서 **cron 등록은 한 번도 실행해 본 적이 없다.**
  `supabase/scheduler.sql` 은 문법만 맞춰 쓴 것이고 실제 등록은 Supabase 에서 확인해야 한다
- 로컬 Postgres 는 16, `supabase/config.toml` 은 17 이다. 버전 차이에 의존하는 기능을 쓰면
  Supabase 스택에서 다시 확인할 것
- 서버 컴포넌트(async)는 Vitest 가 지원하지 않는다. Next 문서 권고는 E2E.
  현재 스모크 테스트는 도구 사슬 확인용이라 이 제약에 걸리지 않았다
- 카카오 로그인·알림톡, 포트원 모두 계정·심사·템플릿 승인이 안 된 상태다

## 다음 사람이 헷갈릴 만한 것
- `needs_operator` 경매는 사람이 손대기 전까지 매 실행마다 계속 보고된다 (해소될 때까지 떠 있는 알림).
  `/admin` 맨 위에서 유찰로 마무리할 수 있다
- 연장 상한 20회는 **경매당**이다 (사용자 확인함). PRD 원문이 "회차당" 이라 잘못 쓰여 있던 것을 고쳤다
- `place_bid` 에서 PRD 에 없지만 판단해서 넣은 것 두 가지:
  1. **첫 입찰은 시작가 그대로 받는다.** PRD 는 "현재가 + 최소 인상폭" 만 적었는데, 그대로 하면
     첫 입찰자가 시작가보다 무조건 더 내야 해서 시작가가 의미를 잃는다.
     입찰 유무는 `highest_bidder_id` 가 아니라 `bids` 로 판단한다 — 최고입찰자가 계정을 지우면 null 이 되기 때문
  2. **마감 시각이 지났으면 status 가 아직 `live` 여도 거부한다.** 스케줄러가 1분 주기라
     마감 직후 몇십 초는 `live` 로 남는다. 이걸 안 막으면 끝난 경매가 입찰로 되살아난다
- `place_bid` 는 `user_id` 를 인자로 받는다. **브라우저에서 직접 호출하면 남의 이름으로 입찰할 수 있다.**
  서버 라우트만 호출하도록 권한을 잠그는 것이 [데이터] 의 "DB 권한 설정" 항목이다. 그 전까지는 노출하지 말 것
- 연락처 미등록 입찰 차단은 `place_bid` 에 아직 없다. [기능] 의 연락처 가드 항목에서 넣는다.
  API 가 아니라 이 함수에 넣어야 한다 — 입찰의 유일한 통로가 여기이기 때문
- 입찰 로직은 애플리케이션이 아니라 Postgres 함수(`place_bid`)에 있다. 앱 코드에서 `bids`/`auctions` 직접 쓰기는 금지 (CLAUDE.md 규칙 목록 참고)
- 이 요약과 `PRD.md` 가 어긋나면 `PRD.md` 가 원본이다
