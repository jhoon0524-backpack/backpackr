### 문제 정의

크라우드펀딩으로만 판매된 창작 굿즈(웹툰·일러스트 굿즈, 보드게임·TRPG 등)는 펀딩 종료 후 정식 유통 경로가 없다. 뒤늦게 알게 된 구매자는 구할 방법이 없고, 보유자는 적정가를 모른 채 중고 커뮤니티에서 선착순 최저가로 넘긴다. 기존 중고 거래는 "먼저 연락한 사람"이 가져가는 구조라 희소 품목의 가격이 발견되지 않고, 판매자·구매자 모두 손해를 본다.

핵심은 이 물건들이 **구조적으로 재생산되지 않는다**는 점이다. 재입고가 불가능하므로 경쟁 입찰이 성립할 조건을 이미 갖추고 있다.

### 가설

종료된 펀딩 리워드만 대상으로, 매주 정해진 시각에 마감을 몰아주면(드롭), 라이브 방송 없이도 경매당 유니크 입찰자 2명 이상이 확보되어 경매가 성립할 것이다.

### 목표

종료된 창작 굿즈를 경쟁 입찰로 거래시켜, 판매자에게는 적정가를, 구매자에게는 구매 기회를 제공한다.

### 성공 지표

| 지표 | 현재 값 | 목표 값 | 측정 방법(데이터 소스) |
|---|---|---|---|
| 경매 성립률 (핵심) | 미측정 (신규) | 드롭 회차가 지날수록 상승하면 유지, 정체·하락하면 카테고리 또는 드롭 주기를 재설계 | 프로덕션 DB. 분모=마감된 경매 수, 분자=유니크 입찰자 2명 이상인 경매 수 |
| 낙찰 후 미결제율 (부작용 감시) | 미측정 (신규) | 회차별로 누적 상승하면 결제 보증 장치(입찰 시 카드 등록 등) 도입 검토 | 프로덕션 DB. 분모=낙찰 건수, 분자=기한 내 결제 미완료 건수 |

- 지표는 2개로 고정한다. 방문자수·등록수는 성패 판정에 필요 없으므로 대시보드에서 보되 성공 지표로 두지 않는다.
- 두 지표 모두 별도 이벤트 로깅 없이 `auctions` / `bids` / `orders` 테이블만으로 계산된다.

### 유저 스토리

- 보유자로서, 소장 중인 종료 리워드의 적정가를 알기 위해 경매로 올리고 싶다.
- 구매자로서, 놓친 펀딩 굿즈를 구하기 위해 마감 시각까지 입찰하고 싶다.
- 구매자로서, 가품을 피하기 위해 판매자의 후원 인증 여부를 확인하고 싶다.
- 구매자로서, 밀린 입찰을 놓치지 않기 위해 상위 입찰 발생 시 알림을 받고 싶다.
- 운영자로서, 가품·정책 위반을 막기 위해 등록된 상품을 공개 전에 검수하고 싶다.

### 기능 명세

**계정**
- 소셜 로그인(카카오)으로 가입하면 이메일·닉네임·연락처를 저장한다.
- 연락처가 미등록이면 상품 등록과 입찰을 차단한다.

**상품 등록 / 검수**
- 판매자가 상품명, 원 펀딩 프로젝트명, 카테고리, 상태 등급, 사진(최소 3장), 시작가, 후원 인증 이미지를 입력하면 `pending` 상태로 저장한다.
- 후원 인증 이미지가 없으면 등록을 거부한다.
- 운영자가 승인하면 다음 드롭 회차에 배정되고 `scheduled`가 된다.
- 운영자가 반려하면 사유와 함께 판매자에게 알린다.
- 시작가는 1,000원 이상이어야 한다.

**드롭 / 경매 진행**
- 드롭 회차는 운영자가 생성하며, 회차에 속한 모든 경매는 동일한 시각에 마감한다.
- 드롭 시작 시각이 되면 배정된 경매를 `live`로 전환한다.
- `live` 상태에서만 입찰을 받는다.

**입찰 (핵심)**
- 모든 입찰은 DB 함수 `place_bid(auction_id, user_id, amount)` 를 통해서만 처리한다. 애플리케이션 코드에서 `bids` / `auctions` 테이블에 직접 쓰기를 금지한다.
- `place_bid`는 대상 경매 행을 잠근 뒤(`SELECT ... FOR UPDATE`) 아래를 순서대로 수행한다.
  1. 경매가 `live`가 아니면 거부한다.
  2. 판매자 본인이면 거부한다.
  3. 현재 최고입찰자 본인이면 거부한다.
  4. 입찰가가 `현재가 + 최소 인상폭` 미만이면 거부한다.
  5. 입찰을 기록하고 경매의 현재가·최고입찰자를 갱신한다.
  6. 마감까지 30초 미만이면 마감 시각을 30초 뒤로 연장한다(경매당 최대 20회).
- 최소 인상폭은 현재가 구간에 따른다. 1만원 미만 500원 / 1만~5만원 1,000원 / 5만원 이상 5,000원.
- 입찰은 취소할 수 없다.

**마감 / 낙찰**
- 1분 주기 스케줄러가 마감 시각이 지난 `live` 경매를 찾아 처리한다.
- 입찰이 1건 이상이면 최고입찰자를 낙찰자로 확정하고 `sold`로 전환한다.
- 입찰이 없으면 `unsold`로 전환한다.
- 이미 `sold` / `unsold`인 경매는 다시 처리하지 않는다(멱등).

**결제**
- 낙찰이 확정되면 낙찰자에게 결제 요청을 보내고 24시간의 결제 기한을 부여한다.
- 낙찰자가 기한 내 결제하면 판매자에게 배송 요청을 보낸다.
- 기한이 지나면 경매를 `payment_failed`로 전환하고 판매자에게 알린다.
- 결제는 PG(포트원 등)를 통해서만 처리하고, 서비스는 결제 수단 정보를 저장하지 않는다.

**알림**
- 상위 입찰이 발생하면 직전 최고입찰자에게 알린다.
- 낙찰·유찰이 확정되면 판매자와 낙찰자에게 알린다.
- 결제 기한 3시간 전에 낙찰자에게 알린다.
- 알림 발송에 실패하면 이메일로 재발송하고 실패를 기록한다.

### 범위

**IN**
- 카카오 로그인
- 상품 등록 + 운영자 수동 검수
- 주 1회 드롭, 동시 마감
- 입찰, 마감 임박 자동 연장
- 자동 마감·낙찰 확정
- PG 결제
- 알림(카카오 알림톡, 이메일 폴백)
- 카테고리 1개로 한정 시작

**OUT**
- 자동입찰(상한 위임)
- 즉시구매
- 차순위 낙찰 이월
- 판매자 정산 자동화 (초기에는 운영자 수동 이체)
- 배송 추적, 분쟁 조정, 판매자 등급, 리뷰
- 검색·필터 (드롭 규모가 작아 목록으로 충분)
- 창작자 리셀 수수료 배분
- 모바일 앱 (웹 반응형만)

### 인수 조건

- Given 경매가 `live`이고 현재가 10,000원, When 서로 다른 사용자 100명이 동시에 11,000원을 입찰, Then 정확히 1건만 성공하고 99건은 금액 부족으로 거부되며 최고입찰자는 1명이다.
- Given 마감 5초 전, When 유효한 입찰이 들어옴, Then 입찰이 기록되고 마감 시각이 30초 연장된다.
- Given 마감 시각이 지난 `live` 경매, When 스케줄러가 두 번 연속 실행됨, Then 낙찰은 1회만 확정되고 알림도 1회만 발송된다.
- Given 입찰이 0건인 경매, When 마감 시각 도래, Then `unsold`로 전환되고 판매자에게 알림이 간다.
- Given 낙찰 후 24시간 경과, When 결제가 없음, Then `payment_failed`로 전환되고 판매자에게 알림이 간다.
- Given 후원 인증 이미지가 없는 등록 시도, When 저장 요청, Then 거부되고 사유가 표시된다.
- [ ] 애플리케이션 코드에서 `bids` / `auctions` 직접 쓰기 경로가 존재하지 않는다 (DB 권한으로 차단).
- [ ] 모든 입찰 시도(성공·거부)가 사유 코드와 함께 기록된다.
- [ ] 마감 처리 스케줄러의 실행·처리 건수가 기록된다.

### 릴리즈 계획

| 단계 | 범위 | 시점 | 롤백 조건 |
|---|---|---|---|
| 1 | 비공개 드롭 1회. 초대된 판매자 5~10명, 상품 10~20개. 실제 결제 포함 | 개발 완료 직후 | 동시 입찰 인수 조건 미통과, 또는 마감 처리 누락 1건 이상 발생 시 공개 중단 |
| 2 | 공개 드롭, 주 1회 정기 운영 | 1단계에서 마감·결제 전 과정이 오류 없이 1회 완주한 뒤 | 결제 오류율이 관측 가능한 수준으로 발생하거나, 미결제율이 회차마다 누적 상승하면 신규 등록을 중단하고 결제 보증 장치를 먼저 도입 |

성공 지표는 2단계부터 측정한다. 1단계는 표본이 너무 작아 성립률 판정에 쓰지 않는다.

### 의존성

- Supabase — 인증, Postgres, Realtime(현재가 갱신), Storage(이미지), pg_cron(마감 처리)
- 입찰 로직은 Postgres 함수 + 행 잠금으로 구현한다. 애플리케이션 레벨 트랜잭션에 의존하지 않는다.
- Vercel — 배포
- Next.js (App Router) + TypeScript + Tailwind
- PG사 — 포트원 등. 가맹점 심사 통과가 2단계 선행 조건
- 카카오 — 로그인, 알림톡 발신 프로필 및 템플릿 사전 승인
- **텀블벅의 어떤 내부 데이터·API·계정도 사용하지 않는다.** 원 프로젝트 정보는 판매자가 직접 입력한 텍스트와 공개 페이지 링크로만 다룬다. 진위 확인은 판매자가 올린 후원 인증 이미지에 대한 운영자 육안 검수로 한정한다.

### 논의사항

- [개발 블로커] 겸업·이해충돌 정리. 현직 텀블벅 사업총괄이 텀블벅 창작물을 대상으로 하는 개인 서비스를 운영하는 구조다. 1단계 착수 전에 회사와 정리해야 하며, 정리 결과에 따라 카테고리나 서비스 성격 자체가 바뀔 수 있다.
- [개발 블로커] 통신판매중개업 신고 및 PG 가맹점 심사. 대금을 서비스가 직접 예치하는 구조는 만들지 않는다. 법률 검토 필요.
