### 문제 정의

크라우드펀딩으로만 판매된 창작 굿즈(웹툰·일러스트 굿즈, 보드게임·TRPG 등)는 펀딩 종료 후 정식 유통 경로가 없다. 뒤늦게 알게 된 구매자는 구할 방법이 없고, 보유자는 적정가를 모른 채 중고 커뮤니티에서 선착순 최저가로 넘긴다. 기존 중고 거래는 "먼저 연락한 사람"이 가져가는 구조라 희소 품목의 가격이 발견되지 않고, 판매자·구매자 모두 손해를 본다.

핵심은 이 물건들이 **구조적으로 재생산되지 않는다**는 점이다. 재입고가 불가능하므로 경쟁 입찰이 성립할 조건을 이미 갖추고 있다.

### 가설

종료된 펀딩 리워드만 대상으로, 매주 정해진 시각에 마감을 몰아주면(드롭), 라이브 방송 없이도 경매당 유니크 입찰자 2명 이상이 확보되어 경매가 성립할 것이다.

> **2026-09-02 — 이 가설과 라이브 경매는 정면으로 어긋난다.**
> 원래 이 제품의 핵심 내기는 "**방송 없이도** 드롭만으로 경쟁이 붙는다" 였다.
> 라이브 경매를 넣는 것은 기능 하나를 더하는 일이 아니라 **내기를 바꾸는 일**이다.
>
> **결정 (2026-09-02): 먼저 잰다.**
> 1단계 드롭을 실제로 한 번 돌려 위 가설을 검증한 뒤에 라이브를 붙인다.
> 검증하지 않은 내기 위에 두 번째 내기를 얹지 않는다.
>
> 라이브를 붙이는 조건은 **성립률**이다. 1단계에서 경매당 유니크 입찰자 2명 이상이
> 확보되지 않으면, 그때 "방송이 성립률을 올린다" 를 새 가설로 세우고 라이브로 간다.
> 성립하면 라이브는 성립률을 더 올리는 수단이지 살리는 수단이 아니게 되므로,
> 그때 다시 값을 따진다.
>
> 그때까지 라이브 경매 명세는 **적어만 두고 만들지 않는다.**

### 목표

종료된 창작 굿즈를 경쟁 입찰로 거래시켜, 판매자에게는 적정가를, 구매자에게는 구매 기회를 제공한다.

### 성공 지표

| 지표 | 현재 값 | 목표 값 | 측정 방법(데이터 소스) |
|---|---|---|---|
| 경매 성립률 (핵심) | 미측정 (신규) | 드롭 회차가 지날수록 상승하면 유지, 정체·하락하면 카테고리 또는 드롭 주기를 재설계 | 프로덕션 DB. 분모=마감된 경매 수, 분자=유니크 입찰자 2명 이상인 경매 수 |
| 낙찰 후 미결제율 (부작용 감시) | 미측정 (신규) | 회차별로 누적 상승하면 결제 보증 장치(입찰 시 카드 등록 등) 도입 검토 | 프로덕션 DB. 분모=낙찰 건수, 분자=기한 내 결제 미완료 건수 |

- 지표는 2개로 고정한다. 방문자수·등록수는 성패 판정에 필요 없으므로 대시보드에서 보되 성공 지표로 두지 않는다.
- 두 지표 모두 별도 이벤트 로깅 없이 `auctions` / `bids` / `orders` 테이블만으로 계산된다.

### 유저 스토리

- 보유자로서, 소장 중인 종료 리워드의 적정가를 알기 위해 경매로 올리고 싶다.
- 구매자로서, 놓친 펀딩 굿즈를 구하기 위해 마감 시각까지 입찰하고 싶다.
- 구매자로서, 가품을 피하기 위해 판매자의 후원 인증 여부를 확인하고 싶다.
- 구매자로서, 밀린 입찰을 놓치지 않기 위해 상위 입찰 발생 시 알림을 받고 싶다.
- 운영자로서, 가품·정책 위반을 막기 위해 등록된 상품을 공개 전에 검수하고 싶다.

### 기능 명세

**계정**
- 소셜 로그인(카카오)으로 가입하면 이메일·닉네임·연락처를 저장한다.
- 연락처가 미등록이면 상품 등록과 입찰을 차단한다.

**상품 등록 / 검수**
- 판매자가 상품명, 원 펀딩 프로젝트명, 카테고리, 상태 등급, 사진(최소 3장), 시작가, 후원 인증 이미지를 입력하면 `pending` 상태로 저장한다.
- 후원 인증 이미지가 없으면 등록을 거부한다.
- 운영자가 승인하면 다음 드롭 회차에 배정되고 `scheduled`가 된다.
- 운영자가 반려하면 사유와 함께 판매자에게 알린다.
- 시작가는 1,000원 이상이어야 한다.

**드롭 / 경매 진행**
- 드롭 회차는 운영자가 생성하며, 회차에 속한 모든 경매는 동일한 시각에 마감한다.
- 드롭 시작 시각이 되면 배정된 경매를 `live`로 전환한다.
- `live` 상태에서만 입찰을 받는다.

**입찰 (핵심)**
- 모든 입찰은 DB 함수 `place_bid(auction_id, user_id, amount)` 를 통해서만 처리한다. 애플리케이션 코드에서 `bids` / `auctions` 테이블에 직접 쓰기를 금지한다.
- `place_bid`는 대상 경매 행을 잠근 뒤(`SELECT ... FOR UPDATE`) 아래를 순서대로 수행한다.
  1. 경매가 `live`가 아니면 거부한다.
  2. 판매자 본인이면 거부한다.
  3. 현재 최고입찰자 본인이면 거부한다.
  4. 입찰가가 `현재가 + 최소 인상폭` 미만이면 거부한다.
  5. 입찰을 기록하고 경매의 현재가·최고입찰자를 갱신한다.
  6. 마감까지 30초 미만이면 마감 시각을 30초 뒤로 연장한다(경매당 최대 20회).
- 최소 인상폭은 현재가 구간에 따른다. 1만원 미만 500원 / 1만~5만원 1,000원 / 5만원 이상 5,000원.
- 입찰은 취소할 수 없다.

**라이브 경매**

기존 드롭(주 1회·동시 마감)과 **별개 모드**다. 둘은 공존한다.
동시 마감은 방송과 양립할 수 없다 — 방송은 한 물건씩 순서대로 올리고 하나씩 마감한다.

- 운영자가 방송을 열고, 배정된 상품을 **한 번에 하나씩** 경매에 올린다. 앞 경매가 끝나야 다음이 시작된다.
- 1단계에서 방송 주체는 **운영자**다. 판매자 개인 방송은 채팅·콘텐츠 관리 부담이 커서 뒤로 미룬다.
- 화면은 세로 9:16 한 벌이다. 위가 영상, 아래가 채팅·현재가·남은 시간이다.
- 남은 시간은 **초 단위**로 센다.
- 입찰 수단은 둘이다.
  - **1클릭 입찰** — 현재가 + 최소 인상폭으로 즉시 넣는다. **확인 창을 띄우지 않는다.**
  - **직접 입력** — 아래에서 올라오는 시트로 받는다. 영상을 가리지 않는다.
- **어떤 입찰 흐름도 영상 위에 전면 팝업을 띄우지 않는다.** 팝업이 뜨는 순간 경매를 놓친다.
  입찰 결과(성공·거부)도 팝업이 아니라 화면 안 문구로 알린다.
- **연장(anti-sniping)** — 마감까지 **5초** 미만일 때 유효 입찰이 들어오면 마감을 5초 뒤로 민다.
  경매당 최대 20회. (기존 드롭 경매는 30초 연장 그대로다. 라이브는 호흡이 빨라 5초로 둔다.)
- **카운트다운과 마감 판정은 서버 시각이 기준이다.** 영상 지연과 무관하다.
- **입찰 순서는 서버 도착 시각으로 판정한다.** 시청자마다 영상 지연이 달라, 화면에서 본 시점과
  서버가 받은 시점이 다를 수 있다. 이 점을 화면에 밝힌다. 이것은 라이브 경매의 본질적 성질이지
  고칠 수 있는 결함이 아니다.
- 채팅은 신고·차단·금칙어를 갖추고, 운영자가 메시지를 지울 수 있다.
- 방송이 끊기면 **경매는 멈추지 않는다.** 남은 시간은 계속 흐르고, 화면에 재접속 안내를 띄운다.
  경매를 방송 상태에 묶으면 방송 사고가 곧 거래 사고가 된다.

**마감 / 낙찰**
- 1분 주기 스케줄러가 마감 시각이 지난 `live` 경매를 찾아 처리한다.
- 입찰이 1건 이상이면 최고입찰자를 낙찰자로 확정하고 `sold`로 전환한다.
- 입찰이 없으면 `unsold`로 전환한다.
- 이미 `sold` / `unsold`인 경매는 다시 처리하지 않는다(멱등).

**결제**
- 낙찰이 확정되면 낙찰자에게 결제 요청을 보내고 24시간의 결제 기한을 부여한다.
- 낙찰자가 기한 내 결제하면 판매자에게 배송 요청을 보낸다.
- 기한이 지나면 경매를 `payment_failed`로 전환하고 판매자에게 알린다.
- 결제는 PG(포트원 등)를 통해서만 처리하고, 서비스는 결제 수단 정보를 저장하지 않는다.

**알림**
- 상위 입찰이 발생하면 직전 최고입찰자에게 알린다.
- 낙찰·유찰이 확정되면 판매자와 낙찰자에게 알린다.
- 결제 기한 3시간 전에 낙찰자에게 알린다.
- 알림 발송에 실패하면 이메일로 재발송하고 실패를 기록한다.

### 범위

**IN**
- 카카오 로그인
- 상품 등록 + 운영자 수동 검수
- 주 1회 드롭, 동시 마감
- 입찰, 마감 임박 자동 연장
- 자동 마감·낙찰 확정
- PG 결제
- 알림(카카오 알림톡, 이메일 폴백)
- 카테고리 1개로 한정 시작
- **라이브 경매** — 세로 방송 + 실시간 채팅 + 초 단위 입찰 (운영자 방송, 순차 진행)
- **모바일 앱** — Expo/React Native. 웹과 같은 서버·같은 규칙을 쓴다

**OUT**
- 자동입찰(상한 위임)
- 즉시구매
- 차순위 낙찰 이월
- 판매자 정산 자동화 (초기에는 운영자 수동 이체)
- 배송 추적, 분쟁 조정, 판매자 등급, 리뷰
- 검색·필터 (드롭 규모가 작아 목록으로 충분)
- 창작자 리셀 수수료 배분
- 판매자 개인 방송 (1단계는 운영자 방송만. 채팅·콘텐츠 관리 부담이 크다)
- 녹화본 다시보기, 클립, 하이라이트
- 방송 중 상품 즉시 추가 (배정된 목록 안에서만 진행한다)

### 엣지케이스

| 카테고리 | 케이스 | 예상 동작 |
|---|---|---|
| 유저 행동 | 두 명이 같은 순간 같은 금액으로 입찰 | 행 잠금으로 직렬화되어 먼저 처리된 1건만 성공, 나머지는 금액 부족으로 거부하고 갱신된 현재가를 반환 |
| 유저 행동 | 판매자가 자기 경매에 입찰 | 거부 |
| 유저 행동 | 현재 최고입찰자가 다시 입찰 | 거부 |
| 유저 행동 | 마감 5초 전 입찰 | 입찰 성공 + 마감 30초 연장 |
| 유저 행동 | 연장이 20회에 도달한 뒤 추가 입찰 | 입찰은 받되 더 이상 연장하지 않음 |
| 라이브 | 마감 3초 전 입찰 | 입찰 성공 + 마감 5초 연장 (라이브 모드) |
| 라이브 | 영상이 3초 늦은 시청자가 "5초 남음"을 보고 입찰 | 서버 도착 시각으로 판정. 이미 마감이면 거부하고 사유를 밝힌다 |
| 라이브 | 방송이 끊김 | 경매는 계속 진행. 화면에 재접속 안내 |
| 라이브 | 방송이 끝났는데 경매가 남음 | 남은 경매는 마감 시각까지 그대로 진행하고 스케줄러가 마감한다 |
| 라이브 | 채팅에 부적절한 내용 | 운영자가 삭제·차단. 금칙어는 자동 차단 |
| 라이브 | 시청자가 몰려 스트리밍 한도 초과 | 영상만 저하·차단하고 **입찰 경로는 유지한다** |
| 유저 행동 | 낙찰 후 결제 미이행 | 24시간 후 `payment_failed`, 판매자에게 알림, 해당 사용자 입찰 제한 검토 |
| 데이터 | 후원 인증 이미지 누락 | 등록 거부 |
| 데이터 | 마감 시각이 이미 지난 상태로 배정 | 배정 거부 |
| 데이터 | 입찰자가 계정을 삭제 | 입찰 기록은 익명 처리하여 보존, 최고입찰이면 낙찰 자격 유지하고 운영자에게 알림 |
| 데이터 | 이미지 용량 초과·형식 불일치 | 업로드 거부, 허용 형식 안내 |
| 외부 시스템 | 스케줄러가 지연되어 마감 처리를 건너뜀 | 다음 실행에서 미처리 경매를 일괄 처리(멱등 보장) |
| 외부 시스템 | PG 승인 실패 | 낙찰 유지, 기한 내 재시도 허용 |
| 외부 시스템 | 알림톡 발송 실패 | 이메일 폴백, 실패 로그 기록 |
| 외부 시스템 | 실시간 연결이 끊김 | 폴링으로 폴백하고 입찰 직전 현재가를 재조회 |

### 인수 조건

- Given 경매가 `live`이고 현재가 10,000원, When 서로 다른 사용자 100명이 동시에 11,000원을 입찰, Then 정확히 1건만 성공하고 99건은 금액 부족으로 거부되며 최고입찰자는 1명이다.
- Given 마감 5초 전, When 유효한 입찰이 들어옴, Then 입찰이 기록되고 마감 시각이 30초 연장된다.
- Given 마감 시각이 지난 `live` 경매, When 스케줄러가 두 번 연속 실행됨, Then 낙찰은 1회만 확정되고 알림도 1회만 발송된다.
- Given 입찰이 0건인 경매, When 마감 시각 도래, Then `unsold`로 전환되고 판매자에게 알림이 간다.
- Given 낙찰 후 24시간 경과, When 결제가 없음, Then `payment_failed`로 전환되고 판매자에게 알림이 간다.
- Given 후원 인증 이미지가 없는 등록 시도, When 저장 요청, Then 거부되고 사유가 표시된다.
- Given 라이브 경매의 마감 3초 전, When 유효한 입찰이 들어옴, Then 입찰이 기록되고 마감이 5초 연장된다.
- Given 라이브 경매, When 영상 스트림이 끊김, Then 카운트다운과 입찰은 정상 동작하고 화면에 재접속 안내만 뜬다.
- Given 라이브 화면, When 1클릭 입찰을 누름, Then 확인 팝업 없이 즉시 입찰되고 영상이 가려지지 않는다.
- Given 영상이 지연된 시청자, When 서버 기준으로 이미 마감된 뒤 입찰, Then 거부되고 "이미 마감되었습니다" 가 뜬다.
- [ ] 애플리케이션 코드에서 `bids` / `auctions` 직접 쓰기 경로가 존재하지 않는다 (DB 권한으로 차단).
- [ ] 모든 입찰 시도(성공·거부)가 사유 코드와 함께 기록된다.
- [ ] 마감 처리 스케줄러의 실행·처리 건수가 기록된다.

### 릴리즈 계획

| 단계 | 범위 | 시점 | 롤백 조건 |
|---|---|---|---|
| 1 | 비공개 드롭 1회. 초대된 판매자 5~10명, 상품 10~20개. 실제 결제 포함 | 개발 완료 직후 | 동시 입찰 인수 조건 미통과, 또는 마감 처리 누락 1건 이상 발생 시 공개 중단 |
| 2 | 공개 드롭, 주 1회 정기 운영 | 1단계에서 마감·결제 전 과정이 오류 없이 1회 완주한 뒤 | 결제 오류율이 관측 가능한 수준으로 발생하거나, 미결제율이 회차마다 누적 상승하면 신규 등록을 중단하고 결제 보증 장치를 먼저 도입 |

| 3 | **라이브 경매** — 1·2단계 성립률을 보고 착수 여부를 정한다 | 2단계 성립률 판정 뒤 | — |

성공 지표는 2단계부터 측정한다. 1단계는 표본이 너무 작아 성립률 판정에 쓰지 않는다.

**3단계(라이브)는 조건부다.** 2단계에서 성립률이 목표에 못 미칠 때 착수한다.
목표를 채우면 라이브는 "필요한 것" 이 아니라 "더 좋게 하는 것" 이 되므로, 그때 값을 다시 따진다.

### 의존성

- Supabase — 인증, Postgres, Realtime(현재가 갱신), Storage(이미지), pg_cron(마감 처리)
- 입찰 로직은 Postgres 함수 + 행 잠금으로 구현한다. 애플리케이션 레벨 트랜잭션에 의존하지 않는다.
- **스트리밍** — 관리형 WebRTC(SFU)를 쓴다. 자체 미디어 서버는 운영 부담이 크다.
  - **경매에서는 지연이 곧 공정성이다.** HLS·LL-HLS(2~10초)는 쓰지 않는다. 5초 연장 창이
    지연보다 짧으면 화면과 서버가 서로 다른 경매를 보게 된다
  - 후보: Amazon IVS Real-Time(서울 리전, 관리형), LiveKit(클라우드·자체호스팅 둘 다 가능), Agora
  - 1단계 권고는 **관리형 서비스**다. 시청자 규모가 커져 비용이 문제가 될 때 자체호스팅을 다시 본다
  - 비용은 시청자-분에 비례한다. 회차별 동시 시청자 수를 먼저 재고 계약한다
  - **영상은 거래 경로가 아니다.** 스트리밍이 죽어도 입찰·마감은 돌아가야 한다
- Vercel — 배포
- Next.js (App Router) + TypeScript + Tailwind
- PG사 — 포트원 등. 가맹점 심사 통과가 2단계 선행 조건
- 카카오 — 로그인, 알림톡 발신 프로필 및 템플릿 사전 승인
- **텀블벅의 어떤 내부 데이터·API·계정도 사용하지 않는다.** 원 프로젝트 정보는 판매자가 직접 입력한 텍스트와 공개 페이지 링크로만 다룬다. 진위 확인은 판매자가 올린 후원 인증 이미지에 대한 운영자 육안 검수로 한정한다.

### 논의사항

- [개발 블로커] 겸업·이해충돌 정리. 현직 텀블벅 사업총괄이 텀블벅 창작물을 대상으로 하는 개인 서비스를 운영하는 구조다. 1단계 착수 전에 회사와 정리해야 하며, 정리 결과에 따라 카테고리나 서비스 성격 자체가 바뀔 수 있다.
- [개발 블로커] 통신판매중개업 신고 및 PG 가맹점 심사. 대금을 서비스가 직접 예치하는 구조는 만들지 않는다. 법률 검토 필요.
> **아래 라이브 관련 4건은 2026-09-02 결정에 따라 보류다.** 1단계 성립률을 재고 나서 답한다.
> 지금 답해 봐야 그 사이에 전제가 바뀐다.

- **[결정 필요 · 라이브] 방송 주체.** 1단계는 운영자 방송으로 적어 뒀다. 판매자가 직접 방송하는
  구조로 갈지, 간다면 언제부터인지 정해야 한다. 개인 방송을 열면 채팅 관리·부적절 콘텐츠 대응
  인력이 그 시간만큼 필요하다.
- **[결정 필요 · 라이브] 기존 드롭과의 관계.** 지금은 두 모드가 공존하는 것으로 적었다.
  라이브로 완전히 갈아탈 것인지(그러면 동시 마감 드롭을 접는다), 둘을 계속 굴릴 것인지.
  둘을 굴리면 운영·화면·규칙이 두 벌이 된다.
- **[결정 필요 · 라이브] 1회 방송 규모.** 한 방송에 몇 개를 올리는지에 따라 방송 길이가 정해진다.
  경매 하나에 2~3분이면 10개는 30분이다. 이 숫자가 상품 배정과 스트리밍 비용을 함께 정한다.
- **[개발 블로커 · 라이브] 라이브 커머스 규제 확인.** 실시간 방송으로 물건을 파는 구조라
  기존 통신판매중개업 신고 범위로 충분한지, 방송 심의·청소년 보호 의무가 걸리는지 확인이 필요하다.
  개인이 파는 중고 물품이라는 점이 일반 라이브 커머스와 다르다.
- [정책 확인] 창작자 리셀 정책. 원작자가 리셀 중단을 요청할 경우의 처리 기준(즉시 내림 / 소명 / 거부)을 1단계 전에 문서로 확정한다.
- [정책 확인] 가품 신고 처리 절차와 판매자 제재 기준.
- 카테고리 선택. 웹툰·일러스트 굿즈와 보드게임·TRPG 중 하나로 시작한다. [데이터 필요: 각 카테고리의 중고 거래 게시글 수·체감 시세] 확인 후 결정.
- 드롭 주기와 시각. 주 1회를 기본으로 하되 1단계 결과로 조정한다.
- 후원 인증 방식. 초기에는 운영자 육안 검수이며 위조를 걸러내지 못한다. 물량이 늘면 대체 수단이 필요하다.
- 수수료율. 1단계는 무료로 운영하고 2단계 진입 시 결정한다.
